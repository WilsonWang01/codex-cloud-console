# Codex Cloud 下一阶段现状与差距分析

日期：2026-10-22，Asia/Shanghai。结论用于确认[下一阶段开发方案](../development-plan-2026-10-22.md)，本轮没有修复代码或部署服务。

## 核心判断

项目已经具备自托管 Codex 控制台、初步个人助理和受限 API 后端的基础。下一阶段最值得投入的是可靠交付：交办后看得见状态，失败后能够恢复，结果能被其他服务取用，用量不会因历史裁剪而失真，个人首页能提出有来源的下一步。

建议定位继续保持为**单用户及其受信任服务使用的云端任务系统**。个人助理、开发工作和外部 API 是三个入口，共用执行、审批、结果和计量。不要同时把项目扩大成通用模型网关、多租户平台和完整云桌面。

当前最显著的产品缺口不是模型数量，而是三种不确定性：用户不知道页面是否真正可用，调用方不知道结果是否完整可取，个人助理不知道哪些跨应用事项值得持续跟进。

## 本轮确认的问题

### R1 已知日用量会受运行历史裁剪影响

优先级 P1。`server/run-safety.mjs` 的 `retainAutomationRuns` 对普通历史默认保留 200 条；`server/run-budget.mjs` 的 `checkKnownTokenBudget` 使用传入运行列表计算当天已知 token。`server/index.mjs` 的 `upsertAutomationRun` 直接把当前运行存储交给预算检查。

纯函数复现：构造同一 UTC 日内 250 条已完成、无外部幂等保护的手动运行，每条 1,000 tokens。完整记录为 250,000，240,000 的门槛应拒绝；裁剪后仅剩 200 条，检查变为允许，显示 200,000。没有运行任何模型，也没有读写生产任务。

这是可复现的计量逻辑缺陷，**不代表已确认用户线上发生超额消费**。当前软门槛本来也不能限制单次执行的实际消耗。先保护当天计量所需记录，随后让用量账本独立于可裁剪运行明细；不能通过扩大列表到另一个固定数字来长期解决。

### R2 首屏可能长时间加载并误导用户判断服务状态

优先级 P1，真实界面症状，根因尚未定位。内置浏览器打开个人今日页后，先显示在线与“正在读取个人空间”，随后显示“连接断开”，主体仍停留在加载文案。之后点击刷新，首页及四条个人会话恢复。

同轮独立 HTTP 抽样返回：`/healthz` 严格健康为真；后续 `/api/status`、个人会话列表及个人简报均为 200，单次耗时分别约 0.76 秒、1.91 秒、0.98 秒。这些请求不是失败当时浏览器请求的完整追踪，不能据此断言只是前端错误或已定位云端故障。

代码中的 `refresh` 先读健康再读大状态接口，失败后将全局状态置为离线；首次成功前 `statusReady` 为假，个人首页被整体挡在加载状态。下一步需要建立同一请求的浏览器、代理、后端证据，并支持局部失败、可恢复超时和最后成功时间。

本机截图保留在 `docs/research/acceptance/next-stage-2026-10-22/today-loading-disconnected.png` 与 `today-recovered.png`，该目录按仓库规则不进入公开 Git。这次只验证了桌面症状与一次刷新恢复，不能据此报告所有断线都已解决。

### R3 已取消运行未正确进入个人变化列表

优先级 P2。`server/personal-brief.mjs` 的 `buildPersonalBrief` 筛选 `cancelled`，而取消接口使用 `canceled`。构造同一条个人任务，`canceled` 产生 0 条变化，改为 `cancelled` 产生 1 条。`PersonalToday` 的运行文案也仅特判 `cancelled`。

应统一内部状态，兼容读取旧拼写；保留历史数据原 ID。不能仅把一处文案改成“完成”。

### R4 用量趋势缺少稳定的历史统计来源

优先级 P1，代码层确认的设计缺口。`server/api-clients.mjs` 按天保存约 30 天请求指标，但 `GET /api/clients/usage` 使用当前可裁剪运行列表聚合 token。请求曲线可以仍有记录，用量数据却已失去对应运行。

应保留独立的按运行/回合计量记录，汇总不依赖会话列表或最近 200 条明细；明确未知、缺失、保留期限和图片工具计量边界。不要用 ChatGPT 订阅 token 数估算真实美元账单。

### R5 显式设置写入仍需要并发保护

优先级 P1，静态风险，未在生产制造竞争。`PATCH /api/chat/sessions/:id/runtime` 先读取会话，随后等待模型查询和 `thread/resume`，再保存配置；没有客户端版本比较或覆盖整个过程的会话级串行保证。两次明确设置请求乱序完成，可能让旧请求最后写入。

10 月 7、8 日的修复覆盖慢速读取和前端切换归属，不能替代两次服务端写请求之间的控制。实现前先用隔离 HTTP 测试复现，再选版本冲突或串行策略。

### R6 首页信息层级与连接信息不够可信

优先级 P2，桌面实际观察：继续对话含日历验收等测试任务，历史条目仅显示时分秒，无法直接分辨哪一天；“安排我的一天”显示日历状态待确认。不能从过去某次授权成功推断此刻可读写。

已有 `isVerificationChatSession` 只识别少量固定标题模式，不能靠扩大正则猜测所有测试内容。建议新增显式用途标签，提供可撤销的隐藏/显示；旧会话迁移由用户选择，保留历史。连接状态显示最近验证时间及能力，首页动作使用同一事实来源。

### R7 架构复杂度开始抵消功能迭代收益

起始提交中的 `src/App.tsx` 为 11,909 行，`server/index.mjs` 为 11,980 行，CSS 为 7,536 行。已经有个人事实、计划、审批、API 等独立模块，说明局部拆分路径可行。

问题不在行数本身，而在会话、运行配置、导航、状态刷新和多个入口共同修改相近状态。应按本轮正在改动的职责提取模块与契约，避免全量框架迁移。当前主包超过 500 kB 的构建提示只是风险信号，不等于已经测得具体设备卡顿原因。

### R8 文档与持续推进缺少统一完成标准

路线图混合了 9 月基线、历史缺陷与最新补丁；`backend-integration.md` 末尾仍有“没有 OpenAI 兼容流式聊天”的旧表述，与文首和后续适配文档冲突。架构文档也没有覆盖现有个人与模型 API 模块。

既有 heartbeat 已启用，但“持续对标直到对等”没有有限完成条件。应维护一个批准后的目标、一个待办序列、一份验收账本，每轮只推进一个完整事项；不能以每日都有提交替代用户任务成功。

## 竞品对标的取舍

以下来自 2026-10-22 重新读取的官方资料，属于产品公开描述，不是账号实测评分。

| 对象 | 最值得借鉴的行为 | 本项目落点 |
| --- | --- | --- |
| Muse | 持续目标、后台活动透明、明确审批、重要变化才通知 | 统一任务详情、下一步与等待原因、可核验结果、低打扰通知 |
| Today | 一天的变化与可编辑记忆结合，建议能进入确认后的行动 | 邮件/日历只读增量、来源时间、行动草案、事实确认和失效管理 |
| Grok Bot | 先把一次任务做对，再保存流程并安排执行；登录受阻时人工接管 | 复用既有试运行门禁，增加结果模板和后续跟进；持久浏览器后置 |
| Codex app-server | 提供线程、事件、审批及模型能力接口 | 继续作为执行基础；新增控制台能力以当前安装版本的契约测试为前提 |
| OpenAI 与 Anthropic API | 标准字段和流式事件具有明确语义 | 兼容范围可发现、可测试；不支持的参数明确拒绝，不用提示词伪装兑现 |

来源：[Muse 设计](https://introducing.muse.ai/)、[Muse 安全设计](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)、[Today 产品说明](https://today.ai/articles/blog/what-is-today)、[Grok 流程](https://docs.x.ai/grok-bot/skills-routines-and-automations)、[Grok 电脑与应用](https://docs.x.ai/grok-bot/computer-and-apps)。

推导出的产品方向：先把三条常见流程做完整，比增加更多模型选项、入口或 Bot 更能缩小体验差距。分别是外部调研到文件交付、个人早间事项到可确认草稿、Issue 到可审阅改动。

Codex 官方建议按场景选用 exec、SDK 或 app-server；本项目需要持久会话和审批，继续使用 app-server 合理。官方协议还列有 `outputSchema`，本地生成类型也存在该字段，因此结构化结果值得优先验证。文档中的能力不证明 EC2 当前 CLI 和账号已经可用。[Codex 集成层选择](https://developers.openai.com/blog/codex-as-a-platform)、[App Server](https://learn.chatgpt.com/docs/app-server)

标准 Responses 有异步查询方式，图片接口有独立的输出控制；Anthropic 的 `max_tokens` 具有输出上限语义。本项目现有子集不能仅通过接受同名字段就宣称兼容。原生工具闭环、硬输出上限和精确图片控制应分别评估，不列为本阶段无条件交付承诺。[Background mode](https://developers.openai.com/api/docs/guides/background)、[图片生成](https://developers.openai.com/api/docs/guides/image-generation)、[Messages](https://platform.claude.com/docs/en/api/messages/create)

## 下一步优先级

1. 修复 R1/R3，复现并解决 R2/R5，建立独立计量与页面级可用性标准。
2. 完成外部 API 的能力发现、结构化结果、受限文件交付、可靠查询与回调，并验收一个真实受信任客户端。
3. 完成一个个人日常流程：经授权的邮件和日历读取、少量重要变化、来源、草稿、待确认和后续跟进。
4. 把上述流程做成一致的手机/桌面交互，补真机、跨天与弱网证据。
5. 在有限目标完成后进行一次阶段评估，再决定是否投入持久浏览器、更多模态和更大范围自动化。
