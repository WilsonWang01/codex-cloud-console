# Personal Agent 第二轮对标与体验审查

日期：2026-09-26。代码基线：`5d07e80`，其中最新运行代码为 `ffe0002`。本文是[统一路线图](personal-agent-roadmap.md)的增量证据和优先级建议，不新建另一套实施方案。

## 一、结论

**现在更像一个功能较全的远程 Codex 控制台，加上个人对话入口；还没有形成每天值得打开的个人助理。** 差距主要不在模型，而在交办、等待、确认、交付、记住偏好、再次执行之间的连续体验。

建议下一轮先完成三件事：

1. 修复统计筛选竞态、移动端空间分配和面板交互，减少已具备能力的使用阻力。
2. 打通“提供材料 → 交办 → 等待确认 → 拿到文件/草稿 → 继续修改”的个人任务闭环。
3. 补齐后台任务的持久状态、结果核验和用量归属，再扩大定时任务及外部服务接入。

不建议继续以“又接入几个模型、工具或 Agent”作为主要进度指标。应看任务是否真正完成、结果能否找到、失败是否能恢复，以及用户需要解释多少次。

### 证据范围

- 本项目：代码阅读、最新验收记录，以及本机代理 `127.0.0.1:18787` 连接生产 API 的浏览器只读检查。使用独立浏览器上下文，不操作用户当前浏览器。
- 浏览器拦截非 GET/HEAD 的 `/api/` 请求；没有提交提示词、上传文件、改变权限、连接邮箱、修改日历或部署。统计竞态使用浏览器内模拟响应，不改生产数据。
- 桌面检查宽度 1280/1440；手机重点检查 390×844，并补充 320px 布局和 390×480 短视口。短视口不是 iOS/Android 真机软键盘验收。
- Muse、Today、Grok Bot、Codex App：核对当前官方产品说明、公开演示和文档；没有登录竞品做真实任务成功率测试，不给未经测量的数字评分。
- 下文“缺失”指本项目未形成可用产品流程，不代表底层 Codex 模型完全做不到。工具可调用也不等于具体业务任务已经验收成功。

## 二、竞品真正值得对标的部分

| 对象 | 官方展示的重点 | 对本项目的启发 | 不应照搬 |
| --- | --- | --- | --- |
| Meta Muse | 持续交办、主对话与旁支、目标/活动视图、独立产物、结构化批准 | 聊天之外能看到任务在做什么、等什么、交付了什么 | 先做人设或视觉装饰，而没有可靠任务状态 |
| Today / today.ai | 今日变化、可修改的个人事实、主动简报、确认后行动 | 首页回答“今天需要我决定什么”，记忆可纠正 | 一开始收集所有生活数据，或把长聊天当作记忆系统 |
| Grok Bot | 常驻执行环境，成功任务沉淀为 Skill，再设 Routine；浏览器接管 | 先跑通一次，再复用和定时；需要人参与时有明确交接 | 多 Bot 数量竞赛，或把共享账号误称为安全隔离 |
| Codex App / Remote | 项目任务组织、运行中排队与补充、审批、审查、附件和结果操作 | 借鉴任务工作台与渐进展开；手机聚焦交办、决策、查看结果 | 把桌面终端、诊断和全部开发设置压缩到手机首屏 |

两个额外边界很重要：

- Muse 公开了执行环境、凭据服务与权限裁决分离的设计。值得借鉴的是“执行者不能自行扩大授权”，不是要求本项目复刻其整套基础设施。[Muse 安全设计](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

## 四、本轮确认的具体问题

### 4.1 用量筛选存在响应竞态：P1，已复现

操作：进入默认 7 天统计，让该请求延迟；切到 30 天并先返回新统计，最后返回旧统计。实际结果是选中“30 天”，请求数却从模拟的 30 变回 7。

原因：[UsageView.tsx](../src/UsageView.tsx) 的 `refresh` 没有 AbortController 或请求序号保护，旧响应仍能写入新筛选的状态。错误响应也可能盖住较新的成功状态。

建议：查询键包含时间范围和调用方；仅当前请求可提交状态。切换期间保留旧图时标注“更新中”，不能把旧图当新筛选结果。补充逆序返回、快速连续切换和卸载测试。

### 4.2 手机首屏被控制区占据：P1，已测量

390×844 的个人对话稳定加载后：顶部导航 97px，会话标题和选择区约 130px，个人说明区约 87px；消息区只有约 315px，约占整个视口的 37%；输入及底部选项约 176px。

这不是单纯字号问题。相同信息反复占位：个人助理标题、个人项目标签、当前会话选择、个人空间说明，同时存在多个新建和会话入口。

建议：小屏只保留一行空间/会话标题与运行状态；历史、重命名、新建收进统一入口。个人权限说明只保留紧凑状态，详细解释按需展开。键盘未打开时，390×844 的消息可见区域目标至少 50%。这是下一轮目标，不是已实现指标。

### 4.3 常用触控入口太小：P1，已测量

手机模型、推理、权限按钮高度 22px；发送和附件按钮 40px；侧栏菜单及面板关闭按钮约 32px 高。部分命令复制按钮只有 26px。

依据：[styles.css](../src/styles.css) 的 `max-width: 820px` 规则及 DOM 实测。应把主要触控热区统一到至少 44×44px，允许图标本身较小；不要依靠扩大字体补救。模型/推理/权限可合为一个会话设置入口，减少底部多行小按钮。

### 4.4 服务连接面板没有形成好用的管理页：P1，已观察

- 390px 首屏里，说明、搜索和 403 提示占了大部分面板，只露出第一项 Sites；邮箱、日历等主要服务需要继续滚动。
- 已标记“可调用”的服务右侧仍显示“暂无授权入口”，容易被理解成未连接或不能用。
- 内部工具和用户关心的邮箱、日历、文档混排，没有“已连接/需要处理/可添加”的顺序。
- 打开面板后焦点仍停在外部触发按钮，按 Escape 没有关闭；容器只是普通 `div`。如果继续作为弹层，需要完整焦点与返回行为；若改独立页，则应按页导航处理，不能两种模式混用。
- 短视口下说明和错误信息进一步挤占服务列表；不能用“没有横向溢出”代替可用性验收。

建议：桌面使用有标题和返回规则的侧面板，移动端独立全屏页。先展示“已连接 9 项”及常用服务，目录错误作为非阻断摘要展开；“可调用”但无专属管理链接时显示“在官方目录管理”，不要展示矛盾的授权缺失状态。上游 403 仍保留详情，不能假装已修好。

### 4.5 个人导航和设置仍偏服务器管理：P1，已观察

个人导航优先展示调用与用量、新对话、设置，没有个人待处理/近期结果入口。个人设置首页主要是 IP、schema、MCP、诊断，右栏仍出现“仓库”“工作区干净”和其他工作任务的日志摘要。

这不构成已证明的后端权限绕过，但破坏个人/工作上下文的前端边界。个人设置应优先放连接服务、记忆与偏好、通知和权限；基础设施放“高级/服务器管理”，工作日志不混入个人页。

代码依据：[App.tsx](../src/App.tsx) 的 `Sidebar`、个人视图限制及设置页右栏。

### 4.6 “有能力”与“可以顺手完成”之间还有断点：P1

“整理文档”已成为首屏建议，但个人空间上传按钮禁用，服务端 `/api/uploads` 直接拒绝个人项目。用户不能直接把截图/PDF/文档交给自己的助理，必须粘贴或绕到外部服务。

建议：上传作为独立、显式的用户操作，写入个人专属附件目录，不依赖给模型全主机写权限。限制大小/类型/路径，支持取消与错误重试，附件生命周期不得误删原文件。随后再形成产物预览、下载及继续修改闭环。

### 4.7 其他已定位的体验风险

| 项目 | 证据与判断 | 优化方向 |
| --- | --- | --- |
| 统计初始状态像“真实零消耗” | `UsageView` 初值全零，无单独 loading 状态；本次移动截图也呈现零值首屏 | 区分加载中、真实零值、部分数据、失败和上次成功更新时间 |
| 图表时区不一致 | 曲线用 `toISOString()` 的 UTC 日期/小时，明细用本地 `toLocaleString()`，页面没有时区标识 | 全页统一显式时区；测试北京时间午夜附近及夏令时 |
| 运行中发送语义单一 | `sendChat` 在忙碌时直接走 `turn-steer`，没有 Queue/Steer 选择 | 默认可见地排队下一条；“立即补充本轮”明确独立，支持撤销未发队列 |
| 自动滚动可能打断回看 | `CloudChat` 在 `messages/busy` 变化时直接滚到底 | 仅在用户接近底部时跟随；否则显示“有新进展”。此项为代码风险，本次未发起付费流式复现 |
| 高级术语占据常用入口 | Goal、ctx、MCP、schema 等与普通任务界面并列 | 默认使用任务、上下文、服务等准确中文；原始信息保留在详情 |

## 五、产品能力缺口与最小实现

| 编号 | 优化项 | 当前不足 | 最小可交付版本 |
| --- | --- | --- | --- |
| C01 | 今日/待处理 | 个人页主要靠用户重开会话查看 | 从已有任务聚合“待你确认、进行中、最近结果”；不开页即调用模型，不先造复杂首页 |
| C02 | 任务闭环 | 对话、Goal、自动化运行与结果分散 | 每次交办可定位任务，显示目标、下一步、等待原因、完成证据；复用现有会话和运行 ID |
| C03 | 首次成功引导 | 四个固定 prompt 不知道服务和材料是否齐备 | 选择一个场景 → 检查所需连接 → 提供输入 → 确认范围 → 获得结果；随时跳过，失败可恢复 |
| C04 | 个人材料与产物 | 上传不支持，图片展示不等于成果管理 | 个人附件、任务结果区、文件预览/下载、来源、版本和继续修改；文件存在及归属可验证 |
| C05 | 业务行动确认 | 已有通用工具审批，缺少用户熟悉的邮件/日程结构 | 邮件收件人/主题/正文/附件或日程时间/时区/参与者预览；编辑后原批准失效，完成保留回执 |
| C06 | 可治理记忆 | 会话历史/记忆引用不等于可编辑个人事实 | 用户明确提供的偏好和事实，可查看、修改、删除、看来源和适用空间；先不自动抽取全部聊天 |
| C07 | Routine | 有自动化基础，但个人用户不能完整创建和管理日常计划 | 从已验收任务保存模板，确认时间/时区/输入/预算/通知，再启用；可暂停、看下次运行、失败原因 |
| C08 | 低打扰通知 | 多通道重试已有，但未成为个人待办工作流 | 只通知结果变化、阻塞或需决定；去重、安静时段、延后和直达任务；通知点击不等于批准 |
| C09 | 连接生命周期 | 可见工具状态，不代表知道哪项授权过期、该怎样续跑 | 任务显示 waiting_auth，连接后继续原任务；区分账号登录、服务授权、云目录受限、本机权限 |
| C10 | 持久浏览器/接管 | 当前自有浏览器入口是一次无头检查，不是可持续云电脑 | 仅在连接器不足的真实场景出现后再做；可见浏览器、受控登录、人工接管和审计，不保证永不重登 |
| C11 | 语音与移动交办 | 当前网页没有完整语音输入/会话流程 | 后置短语音转文本，发送前可编辑；先验证权限、费用、中文输入和上传，不直接承诺实时通话 |
| C12 | 工作模式精细体验 | 已有 Review/Fork/Goal 等基础，不能按完全缺失重建 | 明确工作区、运行中 Queue/Steer、结果到 diff 的短路径；Side Chat 等先做需求验证 |

个人助理和外部 API 后端应共用任务/审批/产物/计量能力，但不共享全部个人记忆。外部调用只能拿到本次任务被允许的上下文。

## 六、前端该怎么重构

### 6.1 信息架构

```text
个人空间
  今日：待确认 / 进行中 / 新结果
  对话：独立上下文、保留草稿和阅读位置
  资料：附件与产物；记忆先作为二级入口
  设置：连接服务 / 偏好 / 权限 / 通知

工作空间
  保留项目、对话、自动化、Review 等开发流程

高级管理
  API 调用与用量 / 服务器 / CLI / 诊断与日志
```

这不是立即新增全部页面。第一步只调整导航与页面职责，今日视图读取现有数据；资料页待个人上传和产物服务完成后加入。无可用数据的入口不做假看板。

### 6.2 对话工作区

- 一个明确的会话标题，标题菜单承担重命名、历史、归档等低频动作；减少同屏重复“个人助理”和新建入口。
- 中间以用户输入、关键进展、待确认、最终结果为主要层级。工具参数、原始日志、token 细节默认收起，但始终可检查。
- 运行状态区回答“正在做什么/为何等待/能否离开页面”；不用只给转圈或在线绿点。
- 结果区集中放成果文件、来源、执行回执和下一步，不让用户在上千行工具消息中寻找下载链接。
- 输入框保持固定且有限高度；模型、推理、权限移入会话设置，但当前权限及模型变化有明确反馈。不能隐藏风险或静默替用户切换昂贵模型。
- 持续运行时分清“排队下一条”和“补充本轮”，失败提示标注是否已被服务端接受，避免用户靠重复点击猜测。

### 6.3 移动端

- 主视图一次只承担一项任务；连接服务、权限和模型设置用全屏面板或底部面板，不叠在窄小输入区上方。
- 没有键盘时优先展示消息；键盘出现后压缩非必要顶栏，保证输入和发送/停止可见。用真实 visual viewport 验证，不只减固定像素高度。
- 关闭按钮、返回手势、Escape 和浏览器返回语义一致；模态面板正确设置标题、焦点进入/归还及焦点约束。
- 不依赖 hover 查看用量或解释。图表允许点击和键盘读值，并提供可读明细；颜色不作为唯一状态提示。
- 长表格在手机改摘要行加详情，文件/图片预览能关闭回原任务，不丢滚动位置。

### 6.4 视觉与性能

统一间距、边框、控件尺寸和字体层级，减少多层框线、大块说明与重复状态色。不需要整站换主题，更不需要为了“像 Codex App”重写组件栈。

已有缓存、按需加载和消息优化应继续复用。优先补测：100 个会话、500 条消息、30 天用量、慢网和断线恢复。温缓存切换 P95 <200ms 作为目标，并分别记录点击反馈、有效内容出现和后台刷新时间；本轮没有得出新的性能 P95，也不能承诺已消除卡顿。

## 七、作为外部 Agent 后端仍缺什么

### 7.1 先有可靠任务契约

现有 API 主要围绕预定义自动化。对外应逐步形成受限异步任务契约：提交拿任务 ID，查询进展/结果，明确取消、超时、重试和待核对；请求与执行必须分别计数。后续 `/v1` 或 MCP 只做同一个服务的适配，不另造执行器。

当前已经避免部分危险重放，但活动运行、事件仍主要保存在内存，JSON 原子写不等于事务队列。应优先用单机事务存储承载新增任务状态、唯一领取、事件序号和通知 Outbox。外部动作已完成但回执没写入时保持待核对，不能自动再发一遍邮件或再创建日程。

### 7.2 用量页从“有柱状图”变成“能定位问题”

保留已实现的调用方与请求/查询/token 统计，补齐：

- 请求 ID → 任务 → 执行尝试 → 模型/推理 → 输入/输出/缓存 token → 结果，能下钻并回到对应任务。
- HTTP 成功率与任务完成率分开；耗时区分排队、模型执行、第三方等待和人工等待。
- 区分外部服务、网页对话和定时任务的覆盖范围；没有采集的消耗标未知，不画成零。当前页面不能被当成全账号账单。
- 显式时区、更新时间、部分数据和保留范围；只读 CSV/JSON 导出，不包含令牌或私密输入。
- 为调用方配置模型范围、并发和预算策略。已知 token 软门槛不是 AWS 账单或模型费用硬上限，不能宣传绝对防扣费。

### 7.3 上游协议与服务承诺

当前官方文档仍注明 app-server 命令及 WebSocket 传输实验性、没有生产工作负载支持；部分插件管理接口也明确处于开发中。本项目启用 `experimentalApi`，并存在插件查询/安装入口。应把这视为集成维护风险，而不是认定当前所有功能不可用。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)

建议：固定已验证 CLI、区分稳定/实验/未知能力、对实验性写操作显式开关、升级契约测试和可回退发布。新增模型可由目录更新，不能因此默认升级全部协议。现阶段适合自托管受控使用，不应向外部客户承诺无条件生产 SLA。

### 7.4 不把“可接 API”说成“竞品已经接通”

Muse/Today/Grok Bot 的账号级自定义接入、鉴权方式和长任务等待仍需分别实测。优先用一个受控参考客户端验收提交、轮询、取消、结果、鉴权和用量，再选择一款实际产品适配。Grok Chat 的连接器能力不能直接当作 Grok Bot 的保证。

## 八、安全与避免过度设计

**发布门禁，不是本轮已确认发生的事故：** 在扩大无人值守外部写操作前，补全参数绑定的业务预览、外部副作用回执、重启核对、凭据边界及预算恢复条件。现有审批代理不能自动等价于所有外部操作都受到独立事务防火墙保护。

与其新建第二套登录/授权中心，应先利用官方服务状态、工具策略和已有审批。不要复制凭据到多个 worker 来伪装“免登录”；不要为避免登录开启新的 AWS 组织、购买服务或增加长效访问密钥。

代码规模已使小改动回归面变大：`src/App.tsx` 约 11,046 行，`server/index.mjs` 约 10,889 行，`src/styles.css` 约 6,984 行。行数不是 bug 证明，但导航、会话、设置、调用用量和权限布局的耦合值得治理。

建议跟随真实需求拆出会话工作区、个人首页、设置/连接、任务服务和用量查询模块；每次拆分保留行为测试。不要为重构而整体迁移框架、引入全局事件总线或多套状态机。

暂不做：多用户 SaaS、人格市场、无限多 Agent、复杂拖拽工作流、向量数据库、独立 OAuth 平台、原生手机 App、完整云桌面和模型智能路由平台。单机 SQLite、现有 React/Express、一个执行适配层足以支持下一阶段。

## 九、建议排期及验收

P1 是下一批优先交付；P2 是后续能力；P3 是需先验证需求。上节发布门禁必须先于对应高风险功能启用，但不要求为只读界面优化先完成全部基础设施。

| 编号 | 优先级 | 交付项 | 归属路线图 | 最低验收标准 |
| --- | --- | --- | --- | --- |
| R2-01 | P1 | 用量筛选竞态、loading、时区 | D3/D4 | 逆序响应不覆盖；失败不显示真实零值；跨日口径一致 |
| R2-02 | P1 | 手机会话框架、触控、面板 | D4 | 390×844 消息区目标 >=50%；主要热区 >=44px；Escape/焦点/返回正确；真机键盘另验 |
| R2-03 | P1 | 服务连接与个人设置分层 | D3/D4 | 已连接与受限目录分开；Gmail/日历可直接找到；个人页不混入工作日志 |
| R2-04 | P1 | 个人附件和结果交付 | D2/D3 | 上传→执行→文件预览/下载→继续修改；跨空间访问拒绝；输入与产物有归属 |

| R2-06 | P1 | 持久任务与结果核验 | D2 | 持久接收后重启不丢；未知副作用不自动重试；结果文件及回执验证 |
| R2-07 | P1 | API 用量下钻与参考客户端 | D3/D6 | 一次任务跨请求/重试只算实际消耗；服务身份、取消、结果和错误可追踪 |
| R2-08 | P1 | 上游能力分级与协议回归 | D4 | 已验证/候选 CLI 的关键契约均有记录；不支持接口可降级，升级不丢任务 |
| R2-09 | P2 | 运行中排队与跟随滚动 | D4 | 排队/补充不同；未发送消息可取消；回看历史时不被流式输出拉到底 |
| R2-10 | P2 | 用户可管理的个人事实 | D5 | 来源与范围可见；修改删除后新任务不使用旧值；历史不可回溯擦除的边界明确 |
| R2-11 | P2 | Routine 与低打扰通知 | D5 | 时区/下次运行/暂停/失败/错过策略可见；无变化不重复通知；有预算授权 |
| R2-12 | P2 | 邮件/日程业务预览 | D7 | 编辑使批准失效；拒绝不执行；超时/重复批准/重启不重复外发 |
| R2-13 | P3 | 持久浏览器、语音、更多外部适配 | D6/D7 | 先有具体阻塞场景、容量/费用评估及用户授权，再单独实施 |

建议按可用闭环切成三批，而非按页面数量验收：

1. **把现有功能变好用：** R2-01/02/03，补权限和状态文案、移动端真机检查；无需新增模型费用。
2. **交办到交付：** R2-04/05/06/08，先用公开资料和用户主动提供的文件验收；真实模型验证单独确认预算。
3. **跨天与多入口：** R2-07/09/10/11，再推进 R2-12；持久浏览器等仍后置。

建议观察指标：首个有效结果耗时、需要用户追问次数、可验证完成率、失败恢复成功率、审批误解次数、重复动作数、有效通知比例。不要把 token 增长或工具调用次数增长当成用户价值。
