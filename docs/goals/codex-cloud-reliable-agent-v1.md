## 目标正文

将 Codex Cloud 完成到“单用户和受信任客户端可以日常依赖”的首版：稳定接收、恢复和交付任务，提供准确可解释的用量、结构化结果和受限文件访问；个人助理能够依据已授权的邮件、日历及显式事实整理今日事项，形成可编辑草稿、明确确认和可核验的后续结果；手机和桌面的核心流程一致可用。

依次完成开发方案 M1-M5。优先处理已知用量裁剪、首屏断线加载、显式设置竞争与取消状态问题，再补 API 能力发现、持久任务与用量、产物交付和回调，最后补个人来源、行动草稿、记忆与低打扰通知。每轮只选一个最高优先级且可完整实现和验收的工作项，完成必要代码 review、自动化和实际 UI 检查后更新证据。

保留已有项目、任务、草稿、凭据和文件；保持现有明确模型选择。复用当前框架、app-server、审批和个人模块，按实际职责逐步拆分大型入口，不重写全系统。新增能力须能在运行时验证，做不到的协议字段明确拒绝。

只在现有授权范围内执行；新增 AWS 资源、未覆盖费用、数据删除、权限扩大、真实邮件发送或日历修改等具体外部动作仍按原规则确认。不得重置额度。模型测试先模拟后真实，记录实际消耗，鉴权失败或结果不明时不得盲目重复。

安全发布前确认任务空闲、备份并验证、检查版本与并行变更，严格健康和实际流程通过后才完成发布；失败保留新旧数据并回退或修复，不覆盖运行中产生的数据。GitHub、EC2、模拟验收和真实业务验收分别记录。

达到开发方案的 API 外部客户端闭环、个人 20 场景至少 18 成功、关键安全场景全通过、真机主要流程和七天观察门槛，且没有 P0/P1 问题后，将本 goal 标记完成并报告残余限制。不得因仍存在可选竞品功能而无限延长，也不得仅因有代码和绿色测试就宣称全面对等。

## 持续推进方式

goal 描述“做成什么”，heartbeat 负责“何时继续”。本机既有“持续优化 Codex Cloud 个人助理”的每日续做保留每天 10:00、`ACTIVE`；2026-10-22 已通过应用工具更新为本方案的 M1-M5 顺序，工具返回更新成功。没有创建第二个定时任务。

2026-10-22 先确认没有活动目标，再创建本原生 goal，工具返回 `active`。未设置 token 数字预算，没有执行额度重置。后续不通过替换目标清零使用记录；已授权持续模型额度不等于财务硬上限。

每轮流程：

1. 读取本文件、开发方案、最近验收、Git 状态及正在执行的工作。检查是否有新的人类要求或其他分支改动。
2. 从下方队列选唯一事项，写明本轮成功条件；有依赖未解决时选择下一项可推进工作，不反复重试同一阻塞。
3. 先复现或建立当前基线，再完成最小合理改动；复用既有模块与测试。纯文档或可逆低风险变更不堆无意义测试。
4. 验证正常、拒绝、断线、重启/并发等与本事项相关路径；涉及页面时通过本机 HTTP 和内置浏览器检查并保存截图。
5. review 授权范围、重复执行、错误终态、数据保留、资源增长与状态竞争；修正后复验。
6. 更新本事项状态和证据；符合既有授权及发布门槛后推送/部署，条件不满足就明确记录尚未上线。
7. 对照阶段退出条件复评，推进下一项。只有重要交付、失败或需用户决定时通知；同状态不重复汇报。

每天自动唤醒一次并不保证连续 24 小时执行，也不证明宿主关闭后一定运行。实际调度结果与运行日志作为依据。用户主动要求继续时可在当前回合连续完成多个独立单元，但不同时发布互相影响的变更。

## 收敛与阻塞

连续两轮没有新证据或实质进展，必须调整方法或说明所缺条件，不为保持活跃而制造样式/文档提交。同一外部阻塞连续三轮且没有可推进工作时，按原生 goal 工具规则标记阻塞，给出具体恢复条件；有独立工作时继续推进。

模型额度不可用、账号权限缺失、容量不足、并行发布冲突等会阻止相应操作，不自动购买、重置、删除数据或修改其他任务。真实七天观察不以加快系统时钟或重复模拟代替。

达到完成清单后停止本 goal 的新增开发，保留普通故障修复建议；现有 heartbeat 若还承担其他目标则不擅自删除，否则按已确认的结束规则停止此项续做。用户可随时调整优先级或明确暂停。
