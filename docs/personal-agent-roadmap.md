## 一、目标与范围

| 需求 | 第一版交付 | 暂不做 |
| --- | --- | --- |
| 独立 Personal Agent | 一个默认个人空间，多个个人对话；与工作项目隔离，随时切换 | 另造聊天引擎、复杂人格市场、多用户 SaaS |
| 外部 API 可观测 | 独立调用方身份、请求曲线、任务结果、token 归属与明细 | 完整计费平台、按推测补齐历史账单 |
| AWS 上手文档与 Skill | 注册、费用说明、选型、连接、部署、验收、数据保护的连续引导 | 一键开通付费套餐、自动创建组织、默认购买长期承诺 |
| 移动端适配 | 交办、切换、审批、结果查看、弱网恢复的完整路径 | 原生 App、离线执行模型、在手机复刻桌面全部工具栏 |

总体定位是**自托管、单用户、多入口的个人任务系统**。同时支持两个使用方向，共用身份、任务、审批、用量、产物和通知服务：

| 使用方向 | 用户如何使用 | 本项目负责 |
| --- | --- | --- |
| 自己的 Personal Agent | 从 Web / 手机个人空间交办日常任务，工作空间继续开发 | 上下文、受控执行、任务状态、审批、记忆与结果交付 |
| 外部 Agent 的 Codex 后端 | 外部服务提交明确任务并获取进展和产物 | 受限异步任务接口、调用归属、用量、取消与恢复 |

外部接入不代表可以替换 Muse、Today 或 Grok Bot 的底层模型，也不默认共享它们的完整个人记忆和高权限账号。首批闭环选择“资料研究简报”和“项目维护报告”，它们与现有能力最接近；邮件、日程、支付、持续浏览器和多 Agent 后置。

优先复用现有项目、会话、app-server、自动化、通知和文件展示。新增领域边界时抽出必要模块，不先对整个后端或前端做框架重写。

### 2.2 原调研基线与缺口

本表及 2.3 保留原提交的发现，不代表当前线上仍存在全部问题。个人空间、真实审批、调用方令牌、幂等摘要、按通道通知和模型发现等已有后续交付；当前差距以 2.4 及最新验收为准。

| 现有基础 | 缺口及设计影响 | 代码入口 |
| --- | --- | --- |
| 项目与会话、草稿、搜索、附件 | 没有独立的个人空间类型；仅加名称或颜色不能隔离上下文 | [App.tsx](../src/App.tsx)、[server/index.mjs](../server/index.mjs)，检索 `selectedRepo`、`chatSessions` |
| 一个 app-server 客户端 | `getAppServerClient` 使用单例及整个 `process.env`；共享系统用户与 Codex 数据不能承诺权限隔离 | 后端 `getAppServerClient` |
| 模型与权限设置 | 当前默认为 `gpt-5.6-terra / medium`、全权限、不请求审批；审批回调还存在自动批准及空回答 | 后端 `defaultRuntime`、`appServerRequestResult` |
| Webhook、Heartbeat、幂等与运行历史 | 使用共享令牌，无法可靠归属调用服务；现有幂等与重启恢复仍需加强 | 后端 `validateAutomationTrigger`、`automationTriggerIdempotencyKey` |
| 会话 token 事件 | 有累计/最近使用量，但不是按调用方、请求、执行轮次保存的用量账本 | 后端 `normalizeTokenUsage`、`thread/tokenUsage/updated` |
| 移动布局、PWA、推送 | 已有 `820px` 断点、安全区与动态视口处理；应改进实际流程，不能按“完全没有适配”重建 | [styles.css](../src/styles.css)、[public](../public) |
| JSON 原子写、有限自动恢复 | 活动运行与事件仍以进程内状态为主，缺少事务接收、唯一领取和持久游标 | 后端 `atomicWriteJson`、`startTurnJob`、`emitJobEvent` |
| 最后一行完成标记 | 不能证明文件存在或外部动作完成，需要结构化结果及确定性校验 | 后端 `completionContract` |
| 多通道通知 | 一个通道成功会使整个事项被标记投递，失败通道不能独立补发 | 后端通知投递逻辑 |
| 线程目标、记忆引用、定时器 | 缺少可管理的长期事实、跨会话目标及带时区和错过运行策略的计划 | 后端自动化与前端 goal / memory 展示 |
| schema 与回归测试 | 固定生成版本不能代替当前运行 CLI 的兼容验证 | [schema 脚本](../scripts/update-codex-app-server-schema.mjs) |
| 单次无头浏览器检查 | 没有持久身份、可见接管和敏感输入通道，不属于完整云电脑 | 后端 `runBrowserCheck` |

**发布门槛：** 个人助理及外部客户端获得写操作前，必须解决真实审批、调用方授权及运行环境隔离。不能仅修改提示词来替代权限控制。现有可信单用户工作模式的变化也要单独说明，不能悄悄改动线上执行行为。

### 2.3 原调研确认的问题

| 优先级 | 证据与影响 | 统一方案中的处理 |
| --- | --- | --- |
| P0 | 命令/文件默认会话级批准，空权限请求仍回应根目录写与联网，提问空答 | 真实待审批/待输入、参数绑定、过期与一次性决定；见 4.3 |
| P0 | 共享 Token、全权限执行器继承控制台环境 | 独立客户端范围、受限 worker、凭据边界；见 4.3、5.1 |
| P0 | 幂等键可省略，相同键未绑定完整输入，部分失败记录重启后可重跑 | 请求摘要、全部终态重放、显式 retry、动作回执；见 3.2、5.1 |
| P0 | 活动任务和事件在内存，没有全局并发与持久领取 | 事务接收、租约、并发准入、事件游标、恢复；见 3.2 |
| P1 | 完成标记仅校验字符串；通知按整条事项标为送达 | 结构化结果与独立通道投递；见 3.3、6.4 |
| P1 | schema 校验固定版本，模型和工具依赖实际运行环境 | Runtime 能力记录与协议矩阵；见 3.4 |
| P2 | 浏览器每次新建后关闭且使用 `--no-sandbox` | 独立浏览器能力评估，不直接扩成外部任意控制接口；见 6.6 |

### 2.4 第二轮对标后的优先级

## 三、统一架构与设计取舍

### 3.1 两份方案的统一决定

| 原有建议的差异 | 整合后的决定 | 原因 |
| --- | --- | --- |
| 独立 Workspace 对象 / 扩展项目类型 | 第一版给现有项目加 `kind`；个人空间不要求 Git。统一使用 `projectId` 表示上下文范围 | 保留现有项目/会话归属，避免两个对象表示同一目录与权限 |
| 今日首页 / 个人对话入口 | 第一版个人对话加紧凑待办、近期结果；记忆与 Routine 可用后再增强今日摘要 | 首页内容需要真实任务数据支撑，打开页面不自动调用模型 |
| 全新 `/v1/tasks` / 复用 Webhook | 先提取共用任务服务并接入现有入口；后续版本化 HTTP/MCP 作为同一服务的适配层 | 保持兼容，防止两套执行和计量逻辑 |
| 事务任务库 / 仅指标 SQLite | 同一单机事务存储承载新增任务控制、审批、调用身份与指标；分模块分表、按阶段加入 | 任务归属与计量需要关联，避免多个库之间缺乏一致性 |
| Agent 可独立于 repo / 仍按项目管理对话 | 任务有独立 ID，但仍绑定明确项目；个人项目可无 Git，一个任务可关联多轮 Run | 会话承担交流，任务承担状态与交付；不丢失授权范围 |
| 全部能力一次补齐 / 四项近期需求 | 当前开发批次是 D1-D4：共同基础、个人空间、API 统计、移动端；D5-D7 保留长期能力 | 原调研的缺口完整纳入，依赖和验收分批落地 |

推荐结构，箭头表示调用关系，不要求拆成多个部署服务：

```text
Web / 手机 / 外部服务
          |
现有 HTTP 入口 -> 后续 /v1 与 MCP 适配
          |
身份、项目范围、输入校验、预算与并发准入
          |
任务服务 -> 审批 / 调度 / 结果与产物 / 通知
          |
单机事务存储 + 现有正文、工作区与 Codex 数据
          |
Runtime Adapter -> 有限且受限的 Codex worker
```

执行器不能修改审批和客户端凭据存储。模块随新增功能抽出，优先 `tasks`、`approvals`、`usage`、`notifications` 和 `runtime-adapter`；保留现有 Review、草稿冲突保护、会话恢复和存储优化。不引入 Kubernetes、服务网格、分布式消息总线或向量数据库。

### 3.2 可靠任务、恢复与动作

沿用已有自动化 Run 与会话关联，补充稳定的任务标识、执行尝试和状态迁移。持久状态至少能表示 `queued`、`running`、`awaiting_input`、`awaiting_approval`、`waiting_auth`、`succeeded`、`partially_succeeded`、`failed`、`canceled`、`needs_reconciliation`。所有入口读同一个事实来源，不能从最后一条聊天文字推断成功。

- **接受与领取：** 校验、幂等记录和任务接收在事务内提交后返回任务 ID；worker 用原子领取、租约及执行代次防止重复领取和过期 worker 写回。进程重启后未领取任务仍在，执行中任务先查实际状态。
- **并发与背压：** 同会话保持串行，加全局与每客户端上限、队列长度和等待超时。队列满返回明确的可重试响应，不无限堆积。待人工输入暂停消耗执行配额，挂起的 runtime/浏览器仍受独立资源上限控制；协议不能安全释放时不得假装已释放。
- **恢复：** 同一提交重放返回原任务，包括失败终态；重新执行是显式 retry，保留 attempt 和预算来源。发现外部写入结果不明时进入核对状态，不仅凭“不要重复执行”的提示词恢复。
- **副作用：** 受控连接器为每次动作保存 `operationId`、参数摘要、审批和回执，能查询第三方结果再决定补偿或重试。任意 shell/网页无法统一保证恰好一次，未经受控执行的任务不授予这项保证。
- **事件：** 状态、审批、错误和产物持久化并有递增游标；高频文本 delta 可有界保留。SSE 用游标续接，历史已裁剪时明确返回快照同步信号，不能伪造完整回放。
- **取消：** 幂等记录取消意图，等待 runtime 确认再标记终态；保留已完成动作，说明取消不能撤回已经发送或发布的内容。

按客户端、任务和 Routine 设置最大时长、重试次数、并发和已知 token 预算。计量不完整时标记原因；任何软预算都不被描述为 AWS 或模型账单的绝对硬上限。费用相关操作仍按用户授权处理。

### 3.3 结果、产物与验收

统一结果包含 `status`、`summary`、`artifacts[]`、`citations[]`、`actions[]`、`checks[]`、`usage`、`error.code`、`retryable`。允许报告部分完成与待核对，运行结束和业务验收分别记录。

产物索引记录 ID、项目、来源任务、版本、类型、路径、内容哈希和保留状态，引用已有文件即可，不移动所有历史附件。下载服务验证项目/调用方范围、规范化路径和符号链接边界；外部客户端不拿任意服务器路径。分享需要明确授权，敏感产物不自动公开。

保留 `exact-final-line` 作为兼容检查；新增确定性校验优先覆盖文件存在、内容哈希、结构化 schema、必要来源和第三方回执。只有模型输出“完成”而文件缺失时，不能报告业务成功。

产物内容可按哈希去重，日志和事件设上限；任务、记忆或用户固定引用的文件不自动清理。清理先报告预计回收量和引用，备份/恢复与状态迁移校验见第九节。

### 3.4 Runtime 与模型兼容

继续使用 app-server，通过单一 Runtime Adapter 接入线程、turn、审批与事件；简单任务以后可评估 SDK，但不能让它形成第二份会话状态。接口资料见 [App Server](https://learn.chatgpt.com/docs/app-server) 与 [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)。

记录实际 CLI 版本、协议能力、模型/推理支持和有效执行参数。测试矩阵包含已验证版本与升级候选版本，不只检查仓库内固定 schema。缺少必要能力时给出具体失败或降级说明；当前新会话默认 `gpt-6-sol / medium`，已有显式模型不静默迁移。

## 四、个人助理空间

### 4.1 产品形态

采用“一个个人空间 + 多个对话”，不是单个无限增长的超级对话，也不要求用户先创建 Git 仓库。

- 桌面侧栏顶部使用“个人 / 工作”切换，文字与图标共同区分，不只靠颜色。个人空间显示对话、待确认事项和最近产物；工作区继续显示项目与开发任务。
- 切到个人空间，回到上次个人对话；首次进入显示可直接输入的新对话。工作区保留原项目、会话、滚动位置和草稿。
- 日常调研、备忘、旅行规划等按主题新建个人对话；不同对话默认不互相注入全文。
- 对话标题、输入区与审批窗口持续显示当前空间。切换不会停止已运行的任务，也不会把正在发送的消息改投到新空间。
- 跨空间协作使用“将选定内容交给工作项目”，先预览将复制的文字和附件，再创建新任务；默认不复制完整历史、私有记忆或工具凭据。
- 新会话默认 `gpt-6-sol / medium`。仅在用户明确指定时提升，实际能力以对应运行环境返回的模型列表为准；不可用时说明原因，不偷偷改用其他模型。

第一版不做独立的复杂“今日仪表盘”。先让用户顺畅完成“打开个人空间 → 交办 → 等待或补充 → 审批 → 查看结果”；日程、长期记忆、主动提醒可在此基础上迭代。复用自动化时，个人任务仍要绑定个人空间，不能回落到第一个工作项目。

### 4.2 数据与上下文边界

采用最小扩展：现有项目增加 `kind: work | personal`，继续以项目 ID 作为所属范围；个人项目的显示名为“个人助理”，其目录不强制是 Git 仓库。第一版只创建一个默认个人空间，避免同时引入 Workspace、Agent、Persona 三套重叠对象。

| 对象 | 归属与限制 |
| --- | --- |
| 对话、执行轮次、产物、自动化 | 必须绑定项目 ID，服务端验证对应关系；不能只相信 URL 或前端过滤 |
| 草稿、上传暂存、搜索缓存、滚动位置 | 缓存键包含项目与对话；切换后不能串用，迟到的异步响应不得覆盖新空间 |
| 指令与个人资料 | 独立指令文件，只加载本空间配置；不继承工作仓库的 `AGENTS.md` 或父目录指令 |
| 记忆 | 首版仅用户可查看、修改的明确资料，不静默抽取全部聊天；未来自动记忆需来源、范围、撤销和删除能力 |
| 搜索与通知 | 默认搜索当前空间；全局搜索显式选择且结果标明归属。通知深链包含空间，但锁屏摘要默认不暴露私密正文 |
| Git、Review、终端 | 非 Git 个人目录不展示无效的 Git/Review 操作；终端与工具权限按空间策略决定 |

新建个人对话只携带该空间允许的指令、用户资料、选定附件及本对话历史。共享模型目录等非私有能力信息可以缓存；个人文档、工具返回和会话摘要不得进入跨空间缓存。

### 4.3 执行隔离与审批

需要区分三个层次：前端区分、模型上下文隔离、执行权限隔离。前两项完成时，不能对外宣传第三项也已完成。

2026-09-26 按用户澄清调整：**默认共用现有 Codex 登录及 app-server，只在项目目录、线程、草稿和前端入口实现上下文分离**。新对话不复用工作线程，也不主动拼入其他空间的消息。共用账号包含额度、全局 Codex 配置、Skills 和 MCP；它不提供系统权限上的保密边界。个人执行默认只读，用户确认后可开启个人工作区写入，保留真实审批，不要求再登录。个人助理提供任务草稿入口和按需服务授权目录；不自动连接邮箱或承诺完整外部事务执行能力。

独立低权限 worker 降为明确选择时的可选部署，不再作为个人空间可用的发布门槛。只有这种模式才需要独立 `HOME` / `CODEX_HOME` / app-server 和专用登录；以下系统级要求仅适用于该模式：

- 个人 worker 不得读取工作仓库、工作 Codex 历史、控制台环境文件和浏览器登录目录；无 sudo、Docker socket 或控制台管理员凭据。
- 工作 worker 也不得读取个人目录与历史。若保留现有工作用户的 sudo/整机访问能力，就只能声明默认上下文分离，不能声称个人数据对工作任务有权限隔离；收紧工作权限需先审核既有任务兼容性。
- worker 启动使用环境变量白名单；个人工具按需授权，不能继承 `process.env` 中全部 AWS、Webhook 和第三方令牌。
- 单独授权该 worker 使用的模型账号，不复制整个现有 Codex 目录。是否支持凭据安全复用需要验证，不承诺“一次登录永久通用”。
- 阻止 worker 借用 EC2 实例角色元数据、localhost 管理接口或其他内部服务绕过边界；不得通过改整机网络规则意外破坏现有工作服务。涉及系统规则变更需单独审批与测试。
- 权限请求必须进入真实待审批状态，超时、断线和无人响应不能默认为同意。决定绑定执行轮次和具体动作；补充信息请求不能回空答案继续跑。
- 审批绑定本人身份、任务、操作参数摘要、范围、期限与一次性 nonce；参数或目标变化使原批准失效。外部服务凭据不得调用审批决定接口。MCP elicitation 根据支持的结构真实展示与回答，不静默拒绝后让用户误以为已授权。
- 临时文件写权限与对外业务动作分开判断。命令黑名单和提示词只能辅助；邮件、购买、云变更等由受控连接器或明确的人工流程执行，不能让任务 shell 修改审批记录或绕过连接器权限。
- 购买、创建计费资源、付款方式变更、公开发布、删除数据等，未有明确范围内豁免时逐项确认；审批记录可追溯。自动化遇到此类操作进入待确认，而不是反复重试。

选用独立 worker 前验证登录、协议、内存开销及文件权限。共享模式按单用户可信部署验收，不将独立登录或双向文件隔离作为其门槛，也不能声称适合恶意多租户。两种模式都必须保留审批、调用方身份与数据归属检查。

### 4.4 迁移与验收

已有项目缺少 `kind` 时按 `work` 读取，已有 ID、路径、会话与运行中任务不变。个人空间按需创建，不能改名或移动旧项目充当个人空间；不能把新进程拿不到的旧对话判成已删除。新增索引先旁路构建，校验数量和引用，再切换读取；回滚保留新增数据并停用新入口，不能用旧版本覆盖新格式状态。

| 编号 | 必须通过的验收 |
| --- | --- |
| PA-01 | 个人与工作往返切换后，草稿、附件、滚动位置及选中对话各自保留；发送过程中切换不串消息 |
| PA-02 | 在两边放入唯一测试标记，检查模型输入、搜索、附件和记忆读取，默认不出现另一边标记 |
| PA-03 | 默认模式复用已有登录、不触发二次授权；个人/工作使用不同 cwd 与 threadId，跨项目选取会话被拒绝。仅专用模式另验收双向文件权限、元数据及管理接口隔离，使用无真实秘密的夹具 |
| PA-04 | 伪造他空间的会话、产物、自动化 ID 被服务端拒绝，深链刷新亦不能绕过 |
| PA-05 | 拒绝、超时、断线、重复审批及重启不造成动作自动执行；补充信息可以真实暂停和恢复 |
| PA-06 | 空工作项目、空自动化列表、无 Git 个人目录都能正常使用；升级后旧任务和数据仍可访问 |

## 五、外部 API 调用方与用量

### 5.1 调用方身份先于图表

在“设置 → API 接入”管理调用服务；主导航提供“调用与用量”。一个服务对应稳定的 `clientId`，例如资料收集器、消息机器人、CI。展示名可修改，历史归属不变。

- 每个调用方使用独立高熵令牌，服务端仅存令牌摘要和可识别前缀；明文只在创建时展示一次，不进入 URL、日志、导出或前端持久存储。
- 权限限定到项目、自动化与操作，例如触发、续跑、读取自己的任务结果；外部令牌不具有管理客户端、看全部会话、修改全局设置的权限。
- 后端从认证结果取得身份；不把调用者提交的 `serviceName`、User-Agent 或源 IP 当作可信归属。
- 支持轮换、撤销、到期、最近调用时间。撤销立即阻止新请求；是否取消已接受任务是另一个需确认的动作。
- 现有共享令牌保留有期限的兼容迁移入口，标为 `legacy-shared`。无法追溯的历史标为“未知调用方”，不根据项目名推断归属。完成各调用端切换后才停用旧令牌。
- 新接口需要幂等键，作用域至少包含调用方和操作；请求摘要包括实际提示词、目标空间/会话、模型与关键执行参数。同键不同请求返回冲突；同请求重放只返回原任务，不再执行。

第一版继续使用现有 Webhook/Heartbeat 执行路径，并加强其认证和幂等；不同时新增一套不兼容的任务执行 API。

### 5.2 页面内容

| 区域 | 内容 |
| --- | --- |
| 调用方列表 | 服务名、启用状态、授权范围、最近调用、请求量、失败率、已知 token 量、数据覆盖率 |
| 时间筛选 | 24 小时、7 天、30 天、自定义；时间按 UTC 存储，按用户选择时区显示并标注 |
| 请求曲线 | 总请求、接受任务、拒绝/限流、HTTP 错误；另列查询/轮询流量，不与执行触发混为一个指标 |
| 任务曲线 | 实际启动与完成、成功/失败/取消、排队时长、执行时长；HTTP 202 不算任务成功 |
| token 曲线 | 输入、缓存输入、输出、推理输出及总量；支持按调用方、实际模型、项目筛选 |
| 明细下钻 | 请求 ID → 任务 ID → 执行轮次 → 结果/错误；幂等重放及恢复链清楚标注 |

成功率标明分母，排队耗时与模型执行耗时分开；P95 使用真实样本或可合并分布计算，不能平均多个区间的 P95。第一版用同一图表切换请求量/token，不堆叠多个重复看板；移动端优先摘要、单图和明细入口。

### 5.3 计量语义与数据模型

新增三类持久记录，不复制聊天正文：

| 记录 | 核心字段 |
| --- | --- |
| `ApiClient` | ID、名称、令牌摘要/版本、范围、状态、创建/撤销时间 |
| `ApiRequest` | 请求 ID、认证后的 clientId、方法与路由模板、接收时间、HTTP 状态/耗时、幂等结果、runId、脱敏错误码 |
| `RunUsage` | runId、attemptId、threadId、turnId、workerId、clientId、projectId、实际模型、起止时间、token 字段、来源与完整性状态 |

记录应有唯一键和事务边界；任务接受时固定调用方归属，不能按“当前会话最后一个调用者”分摊。自动恢复继续原调用方，浏览器人工续写是新的来源；并发、fork、压缩、多轮执行都要有可追踪的计量边界。

token 计算规则：

1. 优先使用协议明确提供的单轮最终用量；流式累计值按同一轮次更新，不把每次事件相加。
2. 只有累计快照时，保存基线与检查点；能证明连续性才做差。压缩、计数重置、分支或丢失基线时标为未知/部分，不靠截断负数假装准确。
3. 缓存输入通常属于输入的子项，推理输出可能属于输出的子项。按实际协议定义展示，不能重复加到总 token；模型上下文百分比也不是消费量。
4. 同一事件重放、页面重连、进程重启不能重复计量；真实重新执行产生的 token 应计入，即使任务失败或被取消。
5. 缺失用量用 `null` 和原因表达，而不是填 `0`；标注覆盖率及未知轮次数。现有 normalizer 的缺字段归零行为不能直接用于用量账本。
6. ChatGPT 订阅额度、token 数与实际美元账单不是同一概念。第一版不做美元费用承诺；以后仅在有明确 API 计价、价格版本及完整用量时提供“估算”，仍与实际账单分开。

指标使用第三节的单机事务存储，由独立模块负责写入、索引、聚合与保留策略，并通过稳定任务 ID 关联执行记录。不要求把现有全部 JSON 状态迁移到数据库。具体 SQLite 驱动在实现时按 Node 22+ 与发布包兼容性验证后选定，不直接修改 Codex 私有数据库 schema。

请求明细拟保留 30 天、小时聚合 90 天、日聚合 365 天，可按磁盘预算调整；这些是新指标的建议默认值，不授权清理现有数据。聚合成功并核对总量后才删除到期指标明细；不级联删除对话、任务、附件、审批证据或用户文件。指标数据库及聚合规则版本纳入备份。

采集入口要覆盖鉴权、校验、限流与内部错误，但不得保存凭据或完整请求体。未认证流量只能标为未知，入口拒绝数据需与代理层日志区分。为恶意高频流量设置有界缓冲/聚合和记录丢失计数；指标异常要可见，不能把缺数据画成零请求。

### 5.4 可观测后的控制措施

支持按客户端请求频率、并发任务数及允许模型限制准入，并保留全局并发上限。普通用户页面只读统计，令牌管理限控制台管理员。跨客户端的结果、附件、SSE 和统计查询都要验证授权。

token 预算可在已知用量超过阈值时暂停接受新任务，但流式上报可能滞后，不能承诺精确的金额硬上限。暂停、恢复或取消线上任务会影响服务，应先说明影响并确认。统计页面不应触发真实模型调用。

| 编号 | 必须通过的验收 |
| --- | --- |
| API-01 | 两个服务调用同一自动化可区分；共享旧令牌只显示共享归属；伪造服务名无效 |
| API-02 | 10 次同键同体触发记录 10 次 HTTP 请求，但只执行一次、消费统计一次；同键异体返回冲突 |
| API-03 | 模拟累计快照 100 → 150 → 150，最终只计 150；重启/重放不增加；重置、缺字段显示部分或未知 |
| API-04 | 一轮 100 输入、其中 40 缓存，20 输出、其中 5 推理时，若协议如此定义，总数为 120 而非 165 |
| API-05 | HTTP 成功但任务失败、取消、恢复后成功及模型切换都能准确下钻，恢复真正消耗的用量不丢失 |
| API-06 | 撤销令牌、跨客户端读取、超限拒绝生效；明细、导出和错误中不含令牌或私密提示词 |
| API-07 | 时区切换、跨日、夏令时、空数据、采集故障、到期聚合均有明确结果；清理不损坏任务资产 |

所有计量验收先用模拟事件和临时状态目录，不为绘制曲线制造付费模型请求。

## 六、日常助理与扩展入口

本节承接原调研中四项近期需求之外的能力。基础结果、通知可靠性和受限接入纳入当前批次；长期记忆、Routine、商业产品适配与浏览器按第九节后续阶段交付。

### 6.1 每日工作闭环与目标

首批验收场景是“资料研究 → 带来源的报告 → 可获取产物 → 重要变化通知”和“项目维护 → 隔离工作区 → 修改/测试 → diff 与审查报告 → 人工决定合并部署”。用完整用户路径校验后端，而非只检查接口是否返回 200。

个人入口逐步补充今天值得处理的变化、等待决定、最近结果；同一份任务数据支持这些视图。跨会话目标增加里程碑、截止日、下一步和等待原因，并可追溯到具体任务。终端、日志和模型细项保留为高级入口，首页不复制一套重型管理后台。

邮件与日程先接只读来源，产出草稿或冲突建议；个人资料整理只处理用户主动提供的文件。外发、改日程、交易、订阅和删除原文件遵循明确授权，不因启用个人助理自动获得权限。

### 6.2 记忆与资料

实际样例补证见[受限配置与记忆验证](acceptance/2026-10-25-personal-memory-quality.md)：3 个本机真实模型回合、虚构资料，候选待确认、引用和更正后新上下文通过；不等于主动记忆质量、线上完整流程或用户评价，E13/E14 和整体 M4 门槛保留。合法插件标识的受限配置代码已随 `70b191f` 发布，生产策略未启用，未扩大权限。

先实现用户明确维护的个人资料，再增加带来源的事实记录与全文检索。记录内容、来源、项目范围、更新时间、有效期和修改历史，区分用户明确陈述与系统推断。

用户修正或删除后，后续检索使用新版本并使相关缓存失效；过期或矛盾事实进入待确认，不自动选择“真实偏好”。已发送到历史对话的内容不能假称被回溯擦除。本人偏好、项目资料和单次任务上下文范围清楚，外部调用只获得该任务必要片段。

个人事实已实现单进程版本校验：跨设备的旧编辑/删除请求不能覆盖最新事实，界面保留未保存输入并要求用户核对后再次保存。原版本事实只读时不改写，损坏文件拒绝变更；这不等于记忆历史、离线编辑同步或多实例事务，见[冲突验收](acceptance/2026-10-04-personal-fact-conflicts.md)。

密码、令牌和验证码不进入记忆；记忆内容不能修改系统权限。先核对 Codex 已有记忆/Skills 的权威来源，建立明确索引与覆盖规则，避免两份互相冲突的事实库。向量检索等待规模和效果证据，不对每条消息额外执行总结与 embedding。

### 6.3 Routine 与主动性

在已有自动化上演进 Routine，增加版本化指令、输入来源、时区、触发条件、错过运行策略、预算、权限和通知规则。自然语言先生成可检查的草案，显示下次运行，确认后启用；可暂停、修改和查看历史。

同一次触发有稳定 `occurrenceId`，固定时间、上游事件和外部结果等待分开处理。明确漏跑是跳过、合并或有限补跑，避免重启后触发大量模型调用。Heartbeat 继续作为续跑机制，不冒充调度器。

用数据版本、增量游标、时间等低成本条件决定是否需要模型处理；是否通知单独判断。无有意义变化保持安静，失败、完成、需要决定和重要变化按用户偏好通知。首个受控 Routine 为研究简报，模型和运行预算在真实连续试用前确定。

### 6.4 通知与连接器

投递按 `事项 + 通道 + 目标 + 版本` 记录，单个通道成功不会掩盖另一个失败。持久 Outbox 支持退避、次数上限和明确的最终失败；重试只针对未成功的目标。安静时间与摘要可配置，关键待审批仍可在应用内找到，送达不等于批准。

连接器展示授权账号、读写范围、有效状态、最近错误及撤销/重连入口。令牌过期进入 `waiting_auth`，暂停依赖它的执行，保留任务和上下文；用户通过受信任认证页面重连，秘密不经聊天转发。入站消息回复需要绑定身份、任务和有效请求，不能把任意消息当作人类授权。

### 6.5 版本化 API 与 MCP

完成任务持久化、权限与用量后，新增薄适配层。以下是后续接口草案，统一调用现有任务服务，不能单独再实现一份队列：

| 接口 | 语义 |
| --- | --- |
| `POST /v1/tasks` | 持久接收 `workflowId + inputs + projectId + policyId`，返回 `202` 与任务查询位置 |
| `GET /v1/tasks/:id` | 返回状态、等待原因、用量与结构化结果 |
| `GET /v1/tasks/:id/events?after=...` | 游标续接或明确快照同步 |
| `POST /v1/tasks/:id/cancel` | 幂等取消，说明已发生的副作用 |
| `POST /v1/tasks/:id/retry` | 显式重试，保留前次结果与核对要求 |
| `GET /v1/artifacts/:id` | 按授权交付对应产物 |
| `POST /v1/approvals/:id/decision` | 只接受本人管理入口的有效决定，服务令牌无权调用 |

MCP 首批仅 `list_workflows`、`submit_task`、`get_task`、`list_artifacts`、`read_artifact`、`cancel_task`；提交快速返回 taskId，按客户端能力轮询或接收通知。不暴露任意 shell、文件读取、云管理、原始 RPC 或自我批准。

先支持轮询，回调仅允许预注册 HTTPS 目标，执行地址和重定向校验、签名、时间戳、重放保护及 Outbox 重试，防止内网探测。一个真实外部客户端完成接入后再标记兼容；Muse、Today、Grok Bot 的待验证范围见第二节。附件、网页和工具返回始终作为数据，不能提升调用方权限。

### 6.6 后续浏览器与委派

持续浏览器需要独立 worker、受限网络/下载、持久身份、认证过期状态、可见接管与敏感输入通道；网站重新认证和人工验证由用户完成。现有烟雾截图能力继续保留，浏览器扩展需单独验证主机容量与安全边界。

多 Agent 从明确父子任务与角色配置开始，继承授权和预算，限制并发、深度及往返次数；交接只带必要输入、结果和来源。不得广播全部记忆或凭据，也不为每个提醒启动永久 Agent。语音输入和跨渠道接管在基础移动流程后评估。

## 八、移动端交互

### 8.1 页面与输入

- 沿用现有移动断点，`<=820px` 以单列主视图为主；小屏顶栏保留空间标识、标题和运行状态，抽屉中切换空间/项目/对话。常用动作不依赖 hover。
- 输入区使用动态视口及安全区，软键盘打开时保持文本、发送/停止按钮可见；中文输入法候选确认不能误发送。
- 模型、推理与权限合并为紧凑入口，在底部面板编辑，保留当前值与费用风险；上传、发送、停止使用带可访问名称的图标按钮。
- 主操作触控区域至少 `44×44 CSS px`；正文与表单可放大，不禁止浏览器缩放。焦点、屏幕阅读顺序、对比度及减少动画偏好都要覆盖。
- 代码/diff 仅在自身区域横向滚动，长链接与路径可断行；图片可预览和关闭，不能撑宽整页。

### 8.2 关键任务路径

| 路径 | 移动端行为 |
| --- | --- |
| 随手交办 | 打开上次空间，输入/上传，一次提交；显示已接受状态，不因响应慢允许重复发送 |
| 切换个人与工作 | 抽屉内明确切换；关闭后回到各自上次位置，未发送附件仍归属原空间 |
| 接收待审批 | 从通知进入目标任务；显示对象、动作和影响，允许拒绝/同意；高风险动作增加具体确认，不能滑动即批准 |
| 长任务与后台恢复 | 离开浏览器不影响服务器任务；回前台先同步服务端状态，再恢复事件流，不重新提交任务 |
| 查看结果 | 先显示最终结果、产物和状态，命令日志按需展开；复制、下载及图片查看可触达 |
| API 用量 | 时间与服务筛选收进面板，单图可切换；明细按行展示核心字段，点击查看完整详情 |

弱网、离线、401、服务重启分别提示。认证失效先保留草稿，再引导登录；离线可保留草稿但不自动排队发送会产生费用的任务。推送权限由用户主动触发，拒绝后仍可通过应用内待办使用，不承诺移动浏览器后台长连接或系统推送必达。

### 8.3 性能与验收

已有会话虚拟化/缓存能力优先复用，日志按需加载、重图表延迟加载，后台页面停止无意义轮询。进入空间先绘制本地壳与有效缓存，再刷新数据；切换时取消过期请求或忽略其结果。避免顶层所有状态更新都重绘长对话。

建议验收预算：同一测试设备上预热后的空间/会话切换可见反馈 P95 小于 200ms；正常网络下无缓存详情首屏目标小于 1s，后端慢时及时显示可取消的加载状态。以上为待实测目标，不是已取得结果。

| 编号 | 必须通过的验收 |
| --- | --- |
| MOB-01 | `320/360/390/430/768/820/1280px` 宽度及手机横屏无整页横向溢出，标题、浮层、按钮不重叠 |
| MOB-02 | iOS Safari、Android Chrome 真机覆盖键盘、安全区、上传和中文输入；桌面 Chromium/WebKit 模拟截图补充，不替代真机 |
| MOB-03 | 200% 缩放、键盘导航、屏幕阅读器、长中英文/路径及大图均可用，模态面板正确管理焦点 |
| MOB-04 | 弱网断线、重复点击、切后台后返回、登录过期，不重复执行任务、不丢草稿、不串空间 |
| MOB-05 | 500 条历史消息、100 个会话、30 天模拟指标下测切换 P50/P95、长任务与内存；报告注明设备/网络/样本 |
| MOB-06 | 升级后的 Service Worker 不混用不兼容前后端；敏感 API 不进入离线共享缓存，更新不强刷掉编辑中的内容 |

### 10.2 测试与报告

先用模拟模型、假连接器和临时目录验证权限、故障、幂等、事件与计量。E2E 使用可控数据覆盖正常路径、拒绝/断线、重启、跨空间访问及手机布局。记录截图、失败复现、运行命令、代码版本、设备/网络与数据规模，不以“页面可打开”代替端到端验收。

review 重点是授权绕过、重复动作、状态竞争、数据丢失、用量误算和回归，也检查模块边界是否引入多余对象或重复状态机。发现按严重程度登记，修复后重跑受影响用例；必需环境缺失写“未验证”，不能标通过。

验收报告应列出各编号的通过/失败/未验证、证据及残余限制；review 报告列问题、影响、修复位置与复验结果。D1-D4 的相关阻断项清零且回归通过后，才能安排线上部署。真机、真实模型、云配置和外部产品适配分别记录验证状态。

性能目标沿用第八节：温缓存切换 P95 <200ms，明确测试环境下任务持久接收 P95 <=1s。模型生成、冷启动、第三方网络、人工等待分别统计。长期效果看有效完成率、重复动作、漏提醒、追问与返工，不把 token 数或 Agent 数当作产品效果；连续一周真实日常试用须有明确预算授权。

### 10.3 开发前的补证事项

EC2 默认共享模式已核验个人与工作读取到同一个有效账号，原有会话和自动化记录保留。真实模型执行、连接器完整能力、可选专用模式的反向权限仍待相应验收。Muse/Today/Grok Bot 的外部接入需各自账号验证。上述未知项限制完整个人 Agent 放行，不撤销已完成的共享登录部署与模拟验收。
