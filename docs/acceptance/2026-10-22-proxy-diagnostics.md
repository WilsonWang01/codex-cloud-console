# 连接异常可追查与安全提示（2026-10-22）

## 选择与边界

本轮先读统一路线图及 10 月 8 日验收，并重新核对 [Muse 产品设计](https://introducing.muse.ai/)、[Today 产品说明](https://today.ai/articles/blog/what-is-today)、[Grok Bot 流程说明](https://docs.x.ai/grok-bot/skills-routines-and-automations)。官方描述的透明状态、连续使用和可靠流程，是选择连接可诊断性的参考，不是竞品实测或能力对等证明。

只完成一个缺口：上轮短暂 502 没有留下可追查记录。新增诊断不能反推出那次故障的根因。本轮首次健康检查为 503，随后恢复正常，账号已验证、无活动任务；没有证据把它等同于上轮代理 502。

## 实现与 Review

- 主代理转发在最终失败、服务器实际 5xx、旧缓存回退或只读重试成功时，最多写一条结构化记录，包含同一请求的错误编号、失败类型、尝试次数及耗时。正常一次成功不记录，不增加依赖、数据库、云监控或服务。
- 日志仅允许固定接口分组和失败码，不保存令牌、查询参数、消息正文、私人文件名、原始异常或服务响应正文。直接转发失败也不再把原始异常文本回传。页面显示中文原因及编号，未知原因安全回退，不改变普通接口错误处理。
- 沿用已有只读重试、超时和通知缓存策略，不让写操作因诊断重放，也不把缓存返回或 503 包装成健康。没有改变账号、默认模型或个人权限。
- 范围是主转发链路，未为 OAuth 辅助转发或后台缓存刷新建立完整追踪。标准错误日志仍由原启动环境保留，并非无限故障下的磁盘硬上限。

## 验收

- 旧代码上的定向测试先失败：超时归类为笼统错误，页面直接回显原始错误文本。修复后安全测试 34 组通过。

- `npm run verify:local` 通过，包含既有本型转接安全测试；最新只读恢复日志判定另重跑 HTTP 回归通过。原有主包超过 500 kB 的提示仍存在。
