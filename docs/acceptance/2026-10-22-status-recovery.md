# F02 首屏加载与断线恢复

日期：2026-10-22。关联：[开发方案](../development-plan-2026-10-22.md) M1/F02、[持续目标](../goals/codex-cloud-reliable-agent-v1.md)。

## 本轮交付

已推送主线：[代码 ca17893](https://github.com/WilsonWang01/codex-cloud-console/commit/ca17893eb01f28bd7f6e9c486df7c1077b3abd2f)、[GitHub CI 39755603600](https://github.com/WilsonWang01/codex-cloud-console/actions/runs/39755603600)。Linux / Node 22 的完整 `verify:local` 及全部步骤成功；EC2 和本机生产代理仍未更新。

健康检查与页面状态并行读取；健康检查等待上限为 5 秒，主状态请求沿用现有 15 秒超时工具。首次失败提供重试及可展开的错误详情，后续失败保留已经加载的页面并显示上次成功读取时间。网络恢复和返回页面时重新读取状态，新的刷新取消旧请求，迟到结果不能覆盖新状态。

快速健康结果不再刷新整份业务数据的生成时间。主状态失败但健康结果可读时，保留已知的在线/降级状态，避免把局部接口错误直接写成断线。健康结果为有效 JSON 时，即使 HTTP 为 503 也保留其中的分层信息。

每轮刷新带一个随机同步编号，可关联浏览器的健康/状态请求和代理故障记录；代理仅保存格式受限的编号，已有脱敏规则保留。浏览器取消这两个只读状态请求时，代理记录断开并释放上游连接。其他业务请求及模型任务不因页面状态刷新而重发或取消。

恢复提示位于顶部状态区，320px 至桌面均可换行；错误详情默认折叠。截图 Review 发现初版提示会被页面布局拉高，已调整结构并补高度断言。

## 复现依据

对修改前 `59ab664` 的真实刷新函数进行隔离探针：使健康请求一直等待，30ms 后主状态请求数量仍为 0。这证实健康检查串行阻塞主请求的路径。代码中两处请求原本均无超时，首次状态失败后仍保留加载文案。

这能解释一种会导致既有症状的路径，不能证明之前真实云端断线只有这一个原因。代理、云端服务或网络仍可能故障；本项让等待有界、失败可恢复并保留可追查信息。

## Review 与发布边界

复用现有 React 状态、请求超时和代理模块，没有新增依赖、数据库或调度器。刷新只读取状态，不自动重放消息或批准请求；取消订阅、切换页面及组件卸载时旧请求失效。保留已有草稿和运行任务。

本机开发候选入口为 `http://127.0.0.1:5174/`，仅监听本机；它经已核实的 `18787` 代理读取云端。若保留预览，它依赖本轮 Vite 进程，停止方式为结束该工作区的 Vite 进程，不能保证机器重启后仍可访问。

EC2 和既有本机生产代理尚未更新，最终上线仍走 M1 的空闲、备份、严格健康与真实流程检查。同步编号关联目前已在隔离代理验收，真实生产代理采用新版后才具备该项日志。F03 服务端设置竞争、F04 状态统一和 F05 发布基线仍未完成。
