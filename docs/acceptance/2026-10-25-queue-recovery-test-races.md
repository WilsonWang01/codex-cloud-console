# 队列恢复验收的计时竞争与限流

状态：[PR #20](https://github.com/WilsonWang01/codex-cloud-console/pull/20) 的代码候选 `fd82f2b71aae3cf0f8363ae6094713ce178d3dbc` 已完成验证，仅验收脚本及证据变化。最终本地 347 项（344 通过、3 项 Linux 专属跳过）/17 组 HTTP、候选 CI 347/347、EC2 四组定向通过；生产代码和服务未变。最终文档/主线检查以 PR 时间线为准，本轮不作为 M2 真实客户端或整体 goal 退出证据。

## 复现证据

上轮 EC2 在“重启后排队/PDF 任务完成”处超出 7 秒；历史失败没有保留任务状态，不能直接认定唯一原因。本轮先保留门槛，复现两种可以造成不可靠验收的机制：

1. 假 CLI 的首任务会在 2600ms 自行结束，但测试假设它在重启前始终占执行位。人为跨过此边界，观察到首任务 completed，第四任务的公开状态仍 queued、SQLite 执行权已经 running，且还没有第四次原生启动请求。这是在准备材料期间已经领取，不是未领取队列；此时重启本应要求核对，不能自动重复执行。r1-r3 的前置状态断言明确失败，不能凭公开 queued 推断安全重放。r4 进一步重启后触发原完成等待失败，但查询限流又遮住了最终状态，不能从该日志断言最终任务状态。
2. 将首任务显式保持，再让假 CLI 后续任务延迟 3000ms，原每 40ms 轮询仍失败。生产接口固定每调用方每分钟 60 次，约 2.4 秒便耗尽查询次数；r5 显示 HTTP 429、Retry-After=54 秒，最后可见任务 running/PDF ready。后续查询即使超过原模拟执行时长也不能取得回执。这证明测试本身触发限流，不等于真实任务丢失。

失败日志均保留在本机 `/tmp/codex-queue-held-first-20261025-r{1,2}.log`、`r3-negative.log`、`r4-negative-restart.log` 和 `/tmp/codex-queue-poll-rate-20261025-r5-negative.log`。受控复现与上轮真实 EC2 历史超时分开记录，不能排他断言它们就是历史唯一根因。

## 最小修复与 Review

- 只对该夹具开启 FAKE_HOLD_QUEUE_FIRST，明确阻止首个模拟回合完成，不修改其他夹具默认计时。等待 2800ms 跨过旧边界，再严格核对首任务 running、第四任务公开 queued/数据库未领取、只有一次原生启动，然后才停止临时进程。
- 同一夹具将后续模拟回合延迟 3000ms，保留慢结果的限流回归，不只测试立即成功路径。
- Review 检查全部首任务计时调用点：回调和受限执行的“重启前保持”场景同样显式保持；确实需要自动完成的限额/聊天排队场景保留原默认行为。回调观察遵守限额，受限执行结果按秒观察，原各自截止时间不扩大。
- 本用例的观察间隔改为 250ms，仍保留原 7000ms 每阶段上限；重启后的完成等待、后续篡改输入验证都遵守真实查询限制。HTTP 非 200 和不应出现的终态立即失败；保留最后有效任务状态、最新 HTTP/Retry-After、观察次数、耗时和重启前状态，不被无正文错误覆盖。
- 重启后仍验证首任务 needs_reconciliation 且不重复，第四任务完成/材料保留/只执行一次，撤销、取消、篡改材料和零用量拒绝等原断言不减少。整个用例包含建夹具、重启及清理，约 18 秒；不是把全用例称为“7 秒内完成”。
- 完整本地首轮还暴露文件交付用例的同类风险：SDK 配置为 50ms，材料领取检查每 5ms 请求公开接口，最终在 file-missing-0004 等待过期。没有把它写成已通过；恢复 SDK 原默认节奏，领取阶段在私有夹具数据库只读观察，仍保留一次真实 HTTP 及“转换尚未完成”的严格断言，原 100 次观察上限不扩大。没有全局限速测试助手，明确的 70 次突发限流测试不改。
- 精确选择单个用例用于诊断，未知名称必须失败，输出 scope=selected；默认执行全部并输出 scope=all。不得用 selected 支持全量通过声明。
- 复用既有脚本、假 CLI、真实 HTTP 和标准库只读 SQLite，无新依赖、应用接口、存储格式、模型调用、后台常驻服务或权限。没有为验收放宽生产限流、改恢复语义或自动重放已领取任务。
