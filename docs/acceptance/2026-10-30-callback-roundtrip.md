# 回调已接收但确认丢失的跨进程验收

## 范围

日期：2026-10-30，Asia/Shanghai。基线 main `8d3dddd`，分支 `codex/callback-roundtrip-acceptance`。推进 M3/A04 的必需故障链路：独立客户端提交任务，接收端已经保存通知，但发送端未收到确认就退出；重启后不能重复任务或重复保存事件，客户端仍能查原结果和文件。

此前发送器的 TLS/重试、接收端的持久化/去重和 API 任务恢复分别有检查，但没有把这次故障串成同一条进程链路。本轮复用实际控制台、任务/回调 SQLite、发送器、独立接收 CLI、Node 客户端与私有文件交付；只新增一个集成检查，不改产品运行时代码、存储格式、依赖或前端。

## 实际过程

1. 本地私有目录创建虚构仓库、调用方和签名密钥。只启动该目录的控制台、独立接收进程及回环 TLS 转发器。
2. 独立客户端只提交一个稳定事件，Codex 替身完成 JSON/报告。实际发送器查询注册、核对公网 IP、签名，经本机 HTTPS 进入真实接收进程。
3. 接收端 SQLite 已提交并返回 202；转发器保持发送方连接，不把确认传回。此时实际 API 显示原任务 completed，通知 sending、attempts=1。
4. 强制结束本轮控制台，保留接收进程及数据库，再用原配置重启。原事件 ID、任务状态、用量和首次发送记录不变。
5. 等真实的 30 秒持久租约到期，不改 SQL、不快进系统时钟。重发同一原始正文，接收端返回 200（重复事件），数据库仍为一条。
6. 发送端记录 delivered、attempts=2。原客户端按通知中的运行 ID 取回 JSON 和原报告，再用原业务键恢复；Codex 替身的 turn/start 仍只有一次，用量页只包含原运行的一条记录。

通知正文仅含事件/运行/自动化编号、终态和相对查询路径；实际核对没有 prompt、报告正文、调用方令牌或签名密钥。事件原始字节、报告内容和完整 SHA-256 都有断言；独立的无密钥只读 CLI 核对唯一接收记录。

## 受控边界

Codex 进程和推理都是替身，真实模型调用为 0。后端 HTTP、存储、回调签名、实际 TLS、接收进程和客户端交付使用真实实现；不能把这当作真实模型质量或生产公网网络验收。

测试专用的子进程预加载模块只为 `callback.test` 返回虚构公网寻址答案，并在发送器完成 IP 固定检查后连接回环 TLS 端口；没有访问该公网 IP。使用临时自签名 CA，实际 TLS 仍核对主机名，负向请求明确返回 `ERR_TLS_CERT_ALTNAME_INVALID`，且未到达接收端。没有关闭证书验证、修改产品 DNS/地址规则、开放公网入口、建立隧道、创建 AWS 资源或登记生产回调。

只强制结束本轮拥有的控制台；Linux 使用原有进程组清理，接收进程持续运行。所有自建服务停止后才清理自有临时目录，原用户项目、任务、草稿、凭据与共享配置不参与测试。没有 UI 变更，不新增页面/手机截图结论。

- 准确候选/主线 CI 以本轮交付回执为准。新增用例包含在普通 `verify:regressions`，不依赖手动开关，不增加单元测试数量；Linux 另有进程组清理，整套应为 20 组 HTTP。这不是个人固定 20 场景的成绩。

可定向重跑（先安装锁定依赖；不请求真实模型）：

```sh

```

仅执行者自查，没有另开 review agent。重点核对了故障发生在持久提交之后/发送确认之前、原进程归属、租约时间、原始正文稳定、签名及隐私、先去重再确认、任务与通知重试分离，以及产物/用量不重复。本轮没有发现需要改动产品运行时代码的问题，不为检查而新增调度器、执行引擎或生产测试开关。
