# 个人流程连接读取失败保护（2026-10-31）

## 范围与复现

本轮从 main `5c28b58` 推进原 P01 / E03 / E08 的一项独立安全缺口，不扩大完整目标。生产发布、真实 MCP 接入、具体回调目标及日历动作仍等待原有对应确认，不复用已消费的单次授权。

当前生成协议的 `ThreadItem` 明确携带 `readOnlyHint`、`status` 和 `error`。使用既有模拟 Codex 和实际控制台 HTTP 后端，先加入失败断言：只读工具 `status: failed`，模型仍声称读取完成，实际试运行却返回 `completed`、没有审核问题；旧计划失败后也仍保留原试运行确认。两项均先失败，后修复。

## 最小实现与 Review

- 仅个人试运行和后台计划记录明确只读调用的失败，使用已有一次性中断机制，不新增执行器或权限层。重复失败通知不会重复中断；普通个人交互和工作对话不套用后台策略。
- 工具失败或错误回执均不能批准试运行，不能被模型的“读取完成”摘要覆盖。已知/未知写入仍优先进入原待核对逻辑，不把可能的外部修改伪装成普通读取失败。
- 计划失败、中断、取消或待核对时，已有暂停分支同时撤销旧试运行确认；后续失败记录使旧成功结果不可重新批准。新的成功试运行仍可确认，不永久锁死流程。
- 工具原始错误不复制到流程错误中。原生回合正常结束时保留准确用量；回合中断时继续标记未知，预算保护不放宽、不清零。
- 复用现有界面的失败、审核问题和禁用状态，没有新增页面或持久状态格式。两个旧 UI 测试改为点击现有应用内确认框，不修改产品删除行为。

## 已完成验收

- 12 项个人流程、计划和外部动作定向通过。实际后端回归覆盖失败状态、带错误的完成回执、无应用上下文、重复回执、原生中断、正常只读、普通个人/工作交互、旧结果拒绝及新试运行恢复。
- 初始整套 `verify:local` 通过：411 项，其中本机 408 通过、3 项 Linux 专用跳过；20 组 HTTP 回归及独立 GitHub API 夹具通过。之后补充的旧结果保护与最终回归再次定向通过。最终准确提交的完整 CI 必须另行核对，见交付回执，不能将此前本机运行冒充最终头完整检查。
- `verify:personal:ui` 重新通过 33 项，包含 7 个宽度、个人/工作草稿、审批隔离和计划启用门禁。初次在旧确认框测试处超时已保留，不计作首次成功。
- 最终后端与构建页面在本机 HTTP 返回 200；内置浏览器实际选择失败流程，桌面、390px 和 320px 刷新后均显示“试运行失败”、不显示“确认结果”、禁用“启用计划”，窄屏无横向溢出。相关截图已保存。临时页面和服务器结束后关闭。
- `node --check server/index.mjs`、`git diff --check` 通过。没有操作真实模型、邮箱、日历、EC2、凭据、信任设置或原有业务任务。

验收过程还保留了两个夹具错误：中断样例放在正常样例之前导致未知用量门禁阻止后续测试，已把中断放最后；复制虚构计划记录时重复原生回合编号触发账本唯一约束，已改成未启动模型的独立零消耗记录。没有通过重置预算或放宽唯一性约束规避失败。

## 尚未覆盖

- `item/completed` 是已结束工具的通知，中断只能请求后续回合停止，不能保证撤销已进行的请求；它也不是独立的事前权限防护。
- 只读声明仍来自上游。这里验证的是协议故障与恢复，不是真实第三方授权撤销，也不自动恢复或重新授权连接。
- 后台暂停/旧确认失效使用真实持久存储与调度单测，读取失败使用实际 HTTP 后端；未合称一个完整线上定时场景。E01–E20、M3–M5、实体手机、七天观察和真人评价原门槛全部保留，不宣称已达 18/20 或全面竞品对等。
- 尚未部署。费用预检确认未答复时不进入 EC2，不因 CI 成功自动绕过发布前空闲、备份恢复和严格健康检查。
