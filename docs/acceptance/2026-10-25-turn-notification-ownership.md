## 复现的问题

上一轮函数级检查发现 `findTurnJob` 只按会话找到当前任务，没有核对通知的回合编号。本轮通过独立调用方令牌、真实 HTTP 控制台与虚构 CLI 完整复现：旧回合的 `turn/completed` 让尚未释放的新任务变为 completed，预期应保持 running。用量、文本、权限和恢复过程也沿用同一错误归属入口。复现只在临时目录进行，没有生产事故发生的证据。

## 最小合理修复

- 继续使用现有会话、任务、所有者索引和审批模块；公共入口同时比较线程、回合和已知条目，完成中/已完成任务不再接收执行通知。不以迟到的 `turn/started` 改写当前编号。
- 新回合编号以启动 RPC 的回执为准。回执前通知在原任务内有界等待，最多 128 条/2 MiB，回执后只按确切归属顺序处理。恢复线程时尚未启动的新任务，不接收旧回合事件。两种 review 模式复用同一逻辑；分离 review 的新线程只在回执确认后绑定，多个等待任务不能重复转发对方的缓存事件。
- 原生压缩接口没有编号回执，以本次请求之后的原生 `contextCompaction` 启动条目及时间确认归属，再等待同一回合的最终成功/失败。不把旧回合完成、条目完成或缺少状态的消息当作成功。
- 审批必须属于当前已确认回合，提前请求等待启动核对；无归属、旧回合及取消任务直接拒绝。用户点击确认时再次检查归属；回合结束关闭它自己的未决审批，不影响其他会话/回合，也不能用旧审批继续批准权限。
- 启动回执缺失、请求失败或通知缓存超限进入待核对，不建立替代线程、不重放模型。已尝试启动但结果不明的用量保持未知，原事件键仍返回同一任务。

不迁移任务/会话数据，不变更模型默认值或已有显式模型，不修改登录、授权范围、个人事实和第三方数据；没有增加依赖或第二套队列。审批关闭逻辑复用一个内部函数，保留失败时清理和拒绝行为。

## Review 与失败记录

第一次完整 HTTP 复现按预期失败：新任务被旧完成事件提前结束。修复后补到回执前、回执后及审批生命周期，不仅测试单个查找函数。原测试夹具曾省略当前原生 schema 必需的回合编号，现按真实 CLI 字段修正；缺编号不冒充有可靠归属。

Review 发现分离 review 的提前通知可能在多个缓存间重新转发，已限制为只处理本次可信回执的归属；个人 worker 先验证空间，再由公共入口核对回合，避免第一个压缩条目在空间检查时被误丢弃。

新增单元测试初次错误地调用只有 resolve 的旧测试辅助函数的 reject，已改用标准 `Promise.withResolvers`。原生负向压缩检查首次触发 CLI 默认重试，超过本机模拟请求上限，整次记失败；明确关闭该模拟 provider 的请求/流式重试后，在三次本机请求内完成正负向验收。没有重试真实鉴权或运行付费模型。

不把模拟消息当作模型质量、竞品能力或生产业务验收。原生启动回执完全丢失时无法凭旧事件安全确定当前编号，需核对原线程，不能保证已开始的外部动作被撤销。
