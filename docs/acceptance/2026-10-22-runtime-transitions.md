# F03 会话设置竞争与任务回写保护

日期：2026-10-22。关联：[开发方案](../development-plan-2026-10-22.md) M1/F03、[活动目标](../goals/codex-cloud-reliable-agent-v1.md)。

## 已复现的问题

在隔离本机 HTTP 服务中，将旧的 GPT-6 Sol 设置请求停在模拟 Codex 的 `thread/resume`，再发 GPT-6 Astra / ultra / 关闭搜索请求。原代码先保存新选择，随后旧请求返回又把模型写回 Sol；新增回归在修复前明确失败。

同时确认任务开始、完成以及设置通知会回写任务启动时的配置，可能覆盖任务运行期间选择的下一轮模型。原来的“运行中不能改权限”只检查请求开始时的状态，后续等待模型目录及协议响应期间仍可能启动任务。

## 实现与语义

- 使用已有按键队列，同一会话的设置请求、普通任务、Review、压缩的启动检查按顺序执行；队列在任务登记为运行中后释放，不等待完整模型回合。不同会话不共用执行锁。
- Web 请求未指定的模型、推理或权限，在进入队列后从最新会话读取；自动化、排队任务或请求明确提供的运行设置继续保留。
- 运行中改权限返回 409。运行中选择下一轮模型或搜索方式只保存待应用配置，不恢复和修改正在运行的上游线程。
- 每次成功保存明确选择生成内部 `runtimeSelectionId`；旧记录默认没有该标记，无需重建数据。线程建立、回合接受、任务结束和设置通知在原子写入内核对标记与实际设置，保留较新的选择。
- 删除/归档中的会话不接受新设置；等待期间会话已消失时返回 404，不返回虚假的保存成功。

“新旧”以服务器进入会话队列的顺序为准，不依赖两台设备的本地时钟。另一设备日后重新提交旧界面的完整设置，仍被视为一条新的明确指令；本项没有声称提供离线冲突合并或客户端版本冲突协议。

## 验收

| 项目 | 证据与结果 |
| --- | --- |
| 慢旧 PATCH 与新 PATCH | 修复前旧模型覆盖；修复后最后保留 Astra / ultra / 关闭搜索，两个请求均按顺序成功 |
| 运行中权限修改 | HTTP 返回 409，原任务继续 |
| 运行中模型选择 | 返回待下一轮应用，`appServerSynced=false`；原任务结束后选择及待应用信息保留 |
| 下一条消息 | 模拟 Codex 的 `turn/start` 实际收到新模型，接受后清除相应待应用信息 |
| 保存权限与任务启动交错 | 旧设置 RPC 未完成前没有 `turn/start`；放行后任务使用新 read-only / on-request 权限 |
| 另一会话 | 当前会话设置 RPC 等待期间，个人会话仍可独立保存设置 |
| 旧任务与明确任务模型 | 安全测试核对较新选择不会被旧任务覆盖；明确的自动化模型仍属于该次运行 |
| 设置通知和旧读取 | 旧通知不能撤销明确选择；此前慢读取、草稿、时间与 pending 保护继续通过 |
| UI 回归 | `verify:runtime:ui` 通过，320/390/1280px、个人/工作两侧，无页面错误和横向溢出 |
| 完整本地回归 | `npm run verify:local` 通过；其后增加的明确任务模型待应用保护单独重跑安全和 HTTP 回归，最终提交由 CI 再验证 |

HTTP 竞争测试使用真实 Express 服务、临时磁盘状态和模拟 Codex 进程；UI 回归使用隔离模拟 API。没有运行真实模型，没有在生产制造竞争或切换用户模型，也没有把这些结果表述成真实手机或生产后端验收。

## Review 与限制

复用现有模块、写入队列和协议参数构造，无新增依赖、数据库或第三方服务。服务端回调只做与本项有关的缩进整理，已用 TypeScript 语法树打印结果核对格式化前后语义一致。

当前目标仍为单机、单后端进程；会话队列不协调多个后端进程。后续请求可能等待前一次设置的协议超时，不代表模型运行队列已经具备持久化。后台任务的明确模型和未来对话的界面选择是两种用途，不把一种静默批量改成另一种。

EC2 尚未更新，发布前仍需空闲、备份、严格健康及真实流程检查。F04 取消状态和 F05 发布基线仍未完成。本轮提交、完整回归及 CI 结果将在发布记录中补充。
