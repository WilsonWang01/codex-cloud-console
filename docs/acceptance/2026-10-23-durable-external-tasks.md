## 实际交付

- 新外部 Webhook、Heartbeat 和模型协议请求先持久接收，再排队执行；不为每个请求创建新服务或新 AWS 资源。
- 在原用量 SQLite 中增加独立任务、幂等和版本表。任务与幂等摘要在一次事务中提交；响应丢失后保持原键、原输入重试，取得同一运行 ID；异体请求返回 409。
- 默认待执行上限 32、app-server 自动化全局并发 2、每调用方并发 1，可按部署配置调整。队列满返回 429；重复请求不会因为队列满而创建另一个运行。并发限制不覆盖直接聊天或 systemd，不是账户总费用上限。
- 未领取的任务重启后继续排队；已领取任务的进程确已退出时进入 `needs_reconciliation`，不自动再执行。领取包含执行者、Linux 启动标识、进程开始时间与代次；旧领取者不能写回覆盖新结果。
- 启动前重新检查调用方的撤销、过期和自动化范围；取消未领取任务不运行模型且用量为零。已开始或结果未知的任务不伪造零用量。
- 排队、执行、待核对任务的原幂等键不会因普通 TTL 到期而失效；已明确结束的任务到期后可接收新运行。待核对任务不自动裁剪，旧 JSON 任务仍使用原保护窗口。
- `startedAt` 保留接收时间，增加可选 `executionStartedAt`。跨 UTC 日期排队的任务按执行开始日记入用量和预算；迟到执行不会因接收时间早于账本窗口而漏记。
- 控制台手动任务、原 systemd 定时服务、项目、聊天与 Codex 自身历史不迁移。新外部任务以 SQLite 为准，JSON 是兼容快照；不引入第二套模型执行器。
- 发布使用原生 `flock` 互斥锁：发布时暂停新接收和队列领取，返回 503/Retry-After；失败回退前检查旧版本是否支持现有任务格式，不用旧状态覆盖新数据。

任务表保存恢复执行所需的原始输入，数据库及备份整体属于敏感数据，权限 `0600`。终态会清空活动行中的执行输入，但不承诺擦除数据库空闲页的旧字节。用量表本身仍不存提示词或完整事件。没有新增依赖、授权范围或公网端口。
