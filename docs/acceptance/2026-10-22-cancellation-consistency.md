## 修复结果

运行记录在服务端读取时，把旧 `cancelled` 规范为 `canceled`；保留任务 ID、时间、事件、调用方归属和用量。没有批量迁移旧文件。只读查询或对已取消任务重复请求取消均不重写运行文件；后续正常持久化时可能把旧状态拼写规范化。

个人简报兼容两种拼写，生成同一规范事件 ID，显示“定时任务已取消”；不再漏掉后台写入的 `canceled`。今日取消结果复用已有状态文案，显示“已取消”，其他结果继续使用原来的完成、失败和“外部操作待核对”提示。个人计划结果也兼容旧拼写，启用/暂停状态仍按计划本身读取，不仅凭取消文案推断。

外部示例客户端接受两种取消终态，立即返回，不额外轮询或重发。已有用量统计继续保留取消前的已知消耗，缺失用量仍为未知，取消不计作成功或失败，也不意味着消耗归零。

`canceling` 仍是进行中的状态：任务收件箱归入活动列表，页面显示“取消中”；个人简报和终态用量统计不会提前把它作为已取消。取消结果不代表撤销已经发生的第三方动作，原来的待核对判断没有改动。

## 复现与验证

新增测试先在旧实现执行：个人简报中的标准取消记录数量为 0；示例客户端把旧拼写取消响应判成无效，两项明确失败。修复后通过。

| 验证 | 实际结果 |
| --- | --- |
| 简报兼容 | `canceled`/`cancelled` 产生相同事件与取消文案，不修改输入；查看后不重复出现，取消中不进入终态简报 |
| 示例客户端 | 两种终态各只提交 1 次请求，没有后续轮询或重发 |
| 用量 | 两种拼写均保留 120 已知 tokens；未知仍为未知；取消中仍处于活动状态 |
| 本机 HTTP/临时磁盘 | 注入旧拼写后，结果查询返回标准状态及原 ID；重复取消返回 200，运行文件字节不变；`turn/start`/`turn/interrupt` 数量不增加 |
| UI 与截图 | 新旧两条取消记录同时进入简报和最近结果，320/390/1280px 显示“已取消”，无横向溢出 |
| 原有个人 UI 回归 | 通过；首次回归发现外部待核对文案被缩短，修正后完整重跑通过 |
| 完整本地回归 | `npm run verify:local` 通过；之后“取消中”分类的两行增量及相关四组 Node 测试再次通过，共 62 项，最终提交由 CI 覆盖 |
| 后端回归 | 9 组通过，含 F01/F02/F03 相关保护、取消、持久数据及安装器回退 |

UI 通过既有本机 Vite 服务与隔离模拟 API 运行，简报数据使用真实的 `buildPersonalBrief` 计算；HTTP 回归使用真实 Express 与模拟 Codex。没有运行真实付费模型、取消生产任务或修改第三方数据。手机为视口模拟，不是真机验收。
