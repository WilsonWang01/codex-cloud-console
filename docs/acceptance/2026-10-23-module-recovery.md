# 旧标签升级资源恢复验收

日期：2026-10-23，Asia/Shanghai。状态：实现及本地验收完成，尚未发布本轮代码；整体 goal 保持 active。

## 问题与改动

上一轮真实发布发现：旧页面仍引用上一版带哈希的分块，服务器移除旧代码后，进入尚未加载的页面会导入失败。原 `React.lazy` 把拒绝交给整棵应用，导致空白；刷新恢复只是临时操作，不是原来的根因修复。

本轮统一 11 个延迟模块的导入：失败只在对应区域显示中文恢复提示，导航、当前会话及其他已加载区域继续保留。原始错误留在浏览器控制台，不把路径或原始异常直接带进页面。没有自动刷新、定时重试、写请求重放、新依赖、后台任务或旧代码常驻。

重新加载必须由用户点击并确认。先保留当前聊天草稿/附件引用和未保存文件编辑（含原文件版本）到既有本机恢复位置，再刷新；本机存储失败或附件上传、提交请求等尚未确认时拒绝刷新。草稿原有服务端保存仍可在本机存储不可用时运行，未修改其并发/版本冲突规则。其他未提交表单不承诺自动恢复，确认框明确提示会关闭这些表单。

设计参考 [Vite 官方加载错误说明](https://vite.dev/guide/build.html#load-error-handling)，并核对本地 Vite 7.3.7 生成代码的 `vite:preloadError` 行为。没有照搬自动 `reload()`：那可能丢失输入或在持续网络错误时循环。HTML 的现有 `no-cache` 规则保持不变。

## 验收与 Review

- 完整本地回归 291 项：288 通过、3 项 Linux 专用跳过、0 失败/取消；15 组隔离 HTTP 回归通过。纯运行时依赖仍 97 包、103,376,234 字节，与锁文件一致。主包约 507.1 kB 的已有规模提醒仍在，没有将本轮称为首屏性能门槛完成。
- 新安全测试覆盖 11 个导入入口、正常加载/拒绝、无自动刷新、用户取消、本机保存成功/失败、附件引用、跨项目文件编辑原版本、上传和提交未确认时拦截。保存失败不阻断原服务端草稿保存路径。
- 双版本构建使用不同真实哈希：旧页面 A 已打开后，静态服务切换为 B，旧 `PersonalFiles` 分块实际返回 404。320/390/1280 三种宽度均出现局部提示、应用主体保留、无横向溢出、按钮至少 44px；取消不刷新，存储不足不刷新，确认后加载 B 并恢复未同步草稿，未发生模型/任务提交。服务仅监听本机、提供临时构建目录，API 为隔离夹具，不接生产数据。
- 桌面内置浏览器实际重复 A→B 流程：输入未发送草稿、切换资料出现恢复提示、重新加载后资料可用、回到原会话文本仍在。点击工具曾超时，之后页面状态和截图确认恢复；不声称工具每步都无异常。截图在忽略目录 `docs/research/acceptance/module-recovery-20261023/iab-upgrade-failure.png` 和 `iab-draft-recovered.png`，不是生产故障注入或真实手机验收。
- 执行者自查，未使用独立 review agent。复用原草稿/文件恢复和 React Context，没有把错误处理分散到 11 份组件，也未改服务端任务、数据库、认证、模型选择、计量或外部动作权限。

验收脚本早期存在两处夹具错误，均未当作产品通过：macOS 临时目录的解析前后路径不同，使安全根目录检查误返回 404；仅加构建注释没有形成不同分块 URL，使旧文件并未真正失效。已核对真实目录，并显式断言 A/B 分块名称不同后重跑成功。

运行 `npm run verify:recovery:ui` 会创建临时两版构建和本机隔离服务，浏览器验收后自动关闭并清理。`--serve-fixture` 仅供人工浏览器验收，需由当前进程停止，不是常驻服务或生产入口。

## 边界和未完成

本轮解决已经加载应用中的分块导入失败，不涵盖入口脚本本身无法下载、所有运行时渲染异常或 F02 的 TLS 网络重置根因。已经打开且尚无本补丁的旧版本不能被远程补入恢复逻辑，需要先完整刷新一次；后续持有本版本的标签才有新保护。
