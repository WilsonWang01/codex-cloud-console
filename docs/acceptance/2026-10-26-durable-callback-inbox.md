# A04 可运行的持久回调接收端

日期：2026-10-26，Asia/Shanghai。基线 `5804e71`，分支 `codex/durable-callback-inbox`。本轮补调用方可直接运行的最小接收端，不改 Codex Cloud 的公网地址校验或自动登记生产回调。最终提交、候选/主线检查和合并以本分支 PR 为准；完整 M2-M5 与原 goal 不提前完成。

## 实际缺口与实现

原示例只有独立验签函数，持久接收、重启去重和容量处理仍需集成方自行实现。新增 `scripts/callback-inbox-example.mjs`，沿用原验签函数和 Node 标准 HTTP/SQLite，不增加依赖或另一套 Codex 执行引擎。

- 明确绑定一个自动化，原始字节验签、核对归属后才持久接收。事务提交后新事件返回 202，相同 ID/相同原始正文返回 200，重试签名时间变化不产生新记录。
- 同 ID 内容变化 409，旧记录和首次接收时间保持；容量满的新通知 503，已有重复事件仍可确认。4096 条/2048 字节的有界记录只追加，不自动删除，不承诺业务处理恰好一次。
- 状态文件识别自身格式与自动化范围；拒绝未知数据库、不安全权限、符号/硬链接，不覆盖旧文件。`--list` 以真正只读方式分页，不启动服务或创建缺失数据库。
- CLI 仅监听回环地址并输出真实端口，HTTP 入口、正文大小、压缩类型和请求接收期限受限；故障不回显密钥或数据库内部错误。临时服务不自动变为常驻服务，不主动发邮件、改日历、查询或重跑模型。
- 较大业务仍应使用自己的接收事务/业务幂等及授权，不因示例存在而宣称生产公网回调已闭环。公网 HTTPS、登记目标和第三方元数据传送仍需具体确认。

## Review 中的修正

首轮实现已通过基本检查；自查发现查看命令可能在路径错误时新建空库，已改为真正只读，并检查文件字节未变及缺失路径未创建。存储已关闭的真实数据库返回 503，不把验签成功当成已可靠接收。

另以签名正确、运行 ID 含无效 Unicode 字符的真实 HTTP 请求复现 `503 !== 401`。原共用验签函数在编码查询路径时抛出未分类异常，接收端会误当临时故障。修复共享路径构造的错误分类，不改变正常签名协议；无效内容现在返回 401，不保存且不诱导无意义重试。

仅执行者自查，没有独立 review agent。重点核对事务提交/确认顺序、并发重复、只读查看、容量拒绝、未知文件保护、密钥不落盘以及接收与业务执行的边界。
